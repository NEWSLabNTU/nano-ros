# C API

The C user-facing surface lives in **`packages/api/nros-c/include/`**, at
upstream's paths (`rclc/`, `rcl/`, `rcl_action/`, ...). `rclc/detail/` is internal.
Generated by Doxygen; always reflects the current `main` branch.

> **Two-layer API.** Every entity exposes two parallel C entry-point
> sets: `rclc_*_init_default` (Layer 1, caller polls) and
> `rclc_executor_add_*` (Layer 2, executor callback). Layer 1
> grew an `_init_polling` + `take_*_raw` / `send_*_raw` family
> for inline-storage callers (no executor arena).
> Layer 2 pairs the same `rclc_*_init_default` with the
> executor-add call, which is where the callback is supplied
> (rclc's binding site). See
> [Two-Layer API](../concepts/two-layer-api.md) for the
> verb discipline and per-layer trade-offs.

> **Event-driven wake callbacks.** Each L1 polling entity supports
> `nros_*_set_wake_callback(entity, &state, cb, ctx)` for event-
> driven RTOS / embassy callers. State is a
> caller-owned `rclc_wake_state_t` POD; the backend fires `cb(ctx)`
> on rx / reply / request arrival. Per-channel for actions
> (`set_{goal,cancel,get_result}_wake_callback` on the server,
> `set_{goal_response,cancel_response,result,feedback}_wake_callback`
> on the client). See the Doxygen for signatures.

## Action server

`<rclc/action_server.h>` follows rclc's model (phase-515 C4):

```c
example_interfaces__action__Fibonacci_SendGoal_Request goal_requests[2];

rclc_action_server_init_default(&server, &node, &support,
    ROSIDL_GET_ACTION_TYPE_SUPPORT(example_interfaces, action, Fibonacci), "/fibonacci");
rclc_executor_add_action_server(&executor, &server, 2, goal_requests,
    sizeof(goal_requests[0]), goal_callback, cancel_callback, &ctx);
```

Each incoming goal takes one of the `handles_number` goal handles
(`rclc_action_goal_handle_t`, at most `NROS_MAX_CONCURRENT_GOALS`); its
request is deserialised into the matching element of the array, and
`goal_callback` returns `RCL_RET_ACTION_GOAL_ACCEPTED` or
`RCL_RET_ACTION_GOAL_REJECTED`. Do the work OUTSIDE the callback — between
`rclc_executor_spin_some()` calls, or from a timer in a C component — and
answer with `rclc_action_publish_feedback(handle, &feedback_message)` and
`rclc_action_send_result(handle, GOAL_STATE_SUCCEEDED, &get_result_response)`.
Two bounds differ from rclc: a goal arriving with every handle in use is
rejected (rclc queues it), and an accepted goal executes at once, so a result
may be sent before the client asks for it. A component, which has no
`rclc_support_t`, passes `NULL` for `support`. See
`examples/linux/c/action-server`.

## Async action client

`<rclc/action.h>` exposes two parallel entry-point families for sending
goals, requesting results, and cancelling:

- **Async (non-blocking):** `rclc_action_send_goal_async()`,
  `rclc_action_get_result_async()`, `rclc_action_cancel_goal()`,
  `rclc_action_try_recv_feedback()`. Return immediately. Replies are
  delivered through the callbacks registered with
  `rclc_action_client_set_goal_response_callback()`,
  `rclc_action_client_set_feedback_callback()`,
  `rclc_action_client_set_result_callback()`, and (for a cancel's reply:
  its return code and how many goals are canceling)
  `rclc_action_client_set_cancel_response_callback()`. The callbacks fire from
  `rclc_executor_spin_some()` — your spin loop is the only place
  callbacks run.
- **Blocking convenience:** `rclc_action_send_goal()` and
  `rclc_action_get_result()`. These call the async variant and then
  drive `rclc_executor_spin_some()` internally on a wall-clock budget
  until the reply lands (or 15 s / 30 s timeout). They take the
  `rclc_executor_t*` explicitly because the action client stores its
  handle as an opaque slot inside the executor (registered via
  `rclc_executor_attach_action_client()`). The same applies to
  `rclc_action_client_wait_for_action_server()` and
  `rclc_action_client_action_server_is_ready()`. Calling any of them
  from inside a dispatch callback returns `RCLC_RET_REENTRANT`.
- **Teardown:** `rcl_action_server_fini()` / `rcl_action_client_fini()`
  reset only the struct. To take an action off an executor that keeps
  running, call `rclc_executor_remove_action_server()` /
  `rclc_executor_remove_action_client()` first: they drop the arena entry
  (the action leaves the graph), free its callback slot and arena bytes for
  reuse, and bring `rclc_executor_get_handle_count()` back down. A program
  that tears the executor down with `rclc_executor_fini()` needs neither —
  that drops every entry (issue 1609).
- **The same holds for every other entity the executor registers** (issue
  1631): `rclc_executor_remove_subscription()`, `rclc_executor_remove_timer()`,
  `rclc_executor_remove_service()` and `rclc_executor_remove_client()` — rclc's
  `rclc_executor_remove_*` shape — each drop the arena entry (receive ring
  included), free the slot and bring `handle_count` back down. Call one before
  the entity's `fini` when the executor keeps running; a timer or client that
  is `fini`'d without it is still dispatched into. A removed client returns to
  INITIALIZED and can be re-added. All return `RCLC_RET_NOT_FOUND` for an
  entity not registered on that executor and `RCLC_RET_REENTRANT` from inside
  a callback. A subscription whose callback also receives the sample's
  attachment is registered with `rclc_executor_add_subscription_with_info()`
  into a `rcl_subscription_t` and removed the same way (issue 1668); the
  older direct-arg `rclc_executor_add_subscription_raw_with_info()` takes no
  subscription object, so its entry lives until `rclc_executor_fini()`.

The equivalent service client helper `rclc_client_call()` does **not**
take an explicit executor — the client stashes the executor pointer
during `rclc_executor_attach_client()` and recovers it internally —
but it follows the same async-then-spin contract.

Canonical pattern: declare the executor, register the client, then
either call the blocking helper or drive `rclc_executor_spin_some()`
yourself between async calls until your callback flags the result. See
the example layouts in `examples/linux/c/action-client/` and
`examples/mps2-an385-freertos/c/action-client/`.

Phase 122.3 added a separate L1 polling family
(`rclc_polling_action_client_init` + the `_raw` send/recv siblings)
that stores `ActionClientCore` inline in the separate type
`rclc_polling_action_client_t` (phase-487 W4) and skips the executor entirely;
see the Doxygen for the full L1 verb list.

## Driving the executor from your own loop

A program that owns its loop (a `while`, an Arduino `loop()`, a PX4 work item)
does not hand the thread to `rclc_executor_spin()`. It drains what is ready
with a zero-timeout spin, then asks how long it may sleep:

```c
for (;;) {
    rclc_executor_spin_some(&executor, 0);
    uint64_t next_ns;
    rclc_executor_get_next_deadline_ns(&executor, &next_ns);
    /* UINT64_MAX: nothing is scheduled; wait for your own events. */
    my_loop_wait(next_ns == UINT64_MAX ? MY_IDLE_NS : next_ns);
}
```

`rclc_executor_get_next_deadline_ns()` (issue 2143, a nano-ros extension) is
the bound the executor's own park uses: the next wall timer, the backend's
next internal event, a supervised route's deadline and every registered wake
source. It answers from now, so time your loop spent between spins is already
counted; `0` means something is due. A ROS-time timer does not bound it (its
wake is a `/clock` message). `UINT64_MAX` is "no deadline", not "never": a
sample can still arrive. The C++ form is `rclcpp::Executor::next_deadline_us`,
and the Rust form `Executor::next_deadline_us`.

## CMake integration

Out-of-tree projects link the `NanoRos::NanoRos` CMake target and
generate C bindings with `nano_ros_generate_interfaces(<pkg> LANGUAGE C)`
(the function defaults to `LANGUAGE CPP`; the full which-spelling table
is in [Message Generation](../user-guide/message-generation.md#which-cmake-spelling-one-table)) —
covered in
[`docs/reference/c-api-cmake.md`](https://github.com/NEWSLabNTU/nano-ros/blob/main/docs/reference/c-api-cmake.md).
