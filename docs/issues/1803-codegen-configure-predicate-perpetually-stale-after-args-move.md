## Measured

Found while measuring issue 1780. `strace -f -e trace=execve` over a NO-CHANGE
reconfigure:

- `examples/native/c/talker` (canonical lane, Unix Makefiles): one
  `nros codegen --language c --args-file …std_msgs.json` per configure;
  `nano_ros_generate_c_args__std_msgs.json` 09:57:54, `std_msgs/nros_message_bounds.cmake`
  09:55:52 (unchanged bytes, never rewritten).
- `examples/zephyr/c/talker` (west, Zephyr 3.7): one `codegen --args-file
  …std_msgs.json` per configure; newest input the args file (10:15:15), oldest
  output `msg/std_msgs_msg_empty.h` (10:09:14).

Both build dirs had once resolved `std_msgs` from a different prefix, which
rewrote the args file (its interface PATHS moved).

## Cause

`nros_codegen_outputs_stale()` (cmake/NanoRosCodegenCore.cmake) is "any INPUT
newer than any OUTPUT". Codegen is write-if-changed per file (so an unchanged
regeneration cascades no rebuild — deliberate), which means after any input
move the outputs whose bytes did not change keep their old mtime and stay older
than the new input for good. The predicate then holds forever: the Zephyr lane
re-runs codegen for the package on every configure, and the canonical lane does
so whenever its fragment check includes the args file.

## Consequence

Cost only — every regeneration after the first is a no-op write, so nothing
rebuilds. But it also made the OLD lanes look as if they caught issue 1780's
in-place `.deb`-mtime change: in a build dir in this state they regenerated by
accident, while a fresh one did not. A predicate that is always true cannot be
distinguished from a correct one by watching it fire.

## Fix direction

Compare against a stamp codegen ALWAYS rewrites when it runs (or the
`nros-generated.toml` record issue 1780 added, compared by CONTENT),
not against every output — the shape `nros_codegen_ament_stale()` already uses.
