# The provider index and the RMW dispatch are two mechanisms that never meet

RFC-0071 D5 says RMW resolution is "BY NAME over a SEARCH PATH OF WORKSPACES",
and its stated acceptance test is "**a fifth backend added out-of-tree with zero
core edits**". The scan half landed. The resolution half did not, and the two
are not connected to each other.

## Measured, both halves, back to back

An out-of-tree provider package, `<ws>/src/acme_rmw/package.xml`, declaring only
`<nano_ros_provides kind="rmw" name="acme"/>`:

```
$ nros ws providers --workspace <ws> --nano-ros-root <repo> --resolve rmw:acme
rmw:acme -> <ws>/src/acme_rmw  [acme_rmw]  root[1] (workspace)
```

The scan finds it, attributes it to root 1, and reports the origin. Now the path
every build actually takes:

```
$ cmake -P probe.cmake     # include(cmake/NanoRosRmwDispatch.cmake)
-- PROBE nros_rmw_is_known(acme) = FALSE
-- PROBE nros_rmw_is_known(uorb) = TRUE
CMake Error at cmake/NanoRosRmwDispatch.cmake:52 (message):
  nros_rmw_dispatch: unknown rmw 'acme' (known: cyclonedds uorb xrce zenoh)
```

Discoverable, not dispatchable. Both commands ran against the same tree, in the
same minute.

## Why — the table is baked at CLI COMPILE time, from `packages/rmw/` only

`packages/cli/cargo-nano-ros/src/rmw_resolver.rs:21`

```rust
include!(concat!(env!("OUT_DIR"), "/rmw_table.rs"));
```

`RMW_ROWS` is generated by `packages/cli/cargo-nano-ros/build.rs:61-124`, which
walks exactly one directory:

```rust
let packages = manifest.ancestors().nth(2)...;   // build.rs:62-67
let rmw_root = packages.join("rmw");             // build.rs:70
```

So the set of resolvable RMW names is fixed when the `nros` binary is compiled,
and is structurally the contents of this checkout's `packages/rmw/`. `build.rs`
says so itself at `:3` and in its header: *"only IN-TREE backends are found here.
An out-of-tree backend needs runtime discovery over a workspace search path,
which is phase-348 and deliberately not this wave."*

Every downstream consumer inherits that closure:
`cmake/NanoRosRmwDispatch.cmake` is `render_cmake_dispatch()`'s output
(`rmw_resolver.rs:179`), `NROS_RMW_KNOWN` at `:58` is its `known_rmw()`.

## The sibling axis already did it, which is what makes this a defect and not a roadmap item

`serdes` — two provisions, the newest family — has both halves wired:

* `packages/cli/cargo-nano-ros/src/serdes_resolver.rs:142` `resolve_serdes` —
  the in-tree `'static` table, same shape as `resolve_rmw`.
* `packages/cli/cargo-nano-ros/src/serdes_resolver.rs:175` **`resolve_serdes_in`**
  — the scan-based one, calling `provider_scan::resolve_unique` at `:180`.

`rmw_resolver.rs` has no `resolve_rmw_in`. Its public surface is
`known_rmw`, `backend_declares_capability`, `backends_declaring`,
`backend_capability_feature`, `canonical_rmw`, `resolve_rmw`,
`render_cmake_dispatch` — every one of them `'static`.

The serdes module states the consequence in its own doc comment
(`serdes_resolver.rs:60-64`):

> Owned `String`s rather than `&'static str` (the RMW resolver's choice) because
> an out-of-repo provider's name is read from a file at selection time and cannot
> be `'static`. **The RMW resolver could stay `'static` only because it has no
> out-of-tree path at all.**

## `nano_ros_load_providers()` has NO production caller

`cmake/NanoRosProviders.cmake:78` is the cmake reader for the index. Repo-wide,
excluding its own definition, the only callers are:

* `packages/testing/nros-tests/tests/provider_index_gate.sh:147` — the gate that
  tests it.
* `packages/testing/nros-tests/tests/negative_diagnostic_registry.rs:55` — a
  reference to that gate.

Three build drivers carry the same comment, verbatim
(`scripts/regenerate-bindings.sh:125`, `scripts/build/fixtures-build.sh:476`,
`scripts/build/workspace-fixtures-build.sh:640`):

> cmake keeps its own index at `${CMAKE_BINARY_DIR}/nros-providers.json` and
> reads it THROUGH the CLI, and **no caller points
> `nano_ros_load_providers(INDEX …)` at the sync-written one.**

The comment is accurate about the sync-written index and understates the
situation: no caller points `nano_ros_load_providers` at *any* index, from any
production configure. The `NANO_ROS_PROVIDER_RMW_<name>_DIR` variables it sets
(`NanoRosProviders.cmake:60-62`) are read by nothing outside the gate.

`nros ws providers --resolve` (`packages/cli/nros-cli-core/src/cmd/ws.rs:839-846`)
is likewise a diagnostic printer — it formats the winner and the shadowed
candidates to stdout and returns; no caller consumes its verdict.

## Scope note: this is not one mechanism, it is four

The four provider kinds all announce themselves identically in `package.xml`
(11 rmw, 39 board, 8 platform, 2 serdes provisions) and are then resolved by
four different mechanisms:

| kind | resolver | out-of-tree? |
| --- | --- | --- |
| serdes | `provider_scan` (RFC-0071 D5) | **yes** |
| platform | `PlatformsTree::default_search_path` + `$NROS_PLATFORMS_DIR` (`nros-cli-core/src/cmd/board_facts.rs:104-125`) | yes, separate path |
| rmw | compile-time `RMW_ROWS` | **no** |
| board | `board_facts` / `NROS_BOARD_TOML` | not established |

The uniform announcement reads as a uniform seam and is not one. RFC-0071 D8
("one descriptor family: rmw, platform, board") is the design that would make it
one; it has not been applied to discovery, only to descriptors.

## Why it matters

* RFC-0071's own acceptance test is unmet, and the RFC says so: *"until that is
  demonstrated the RFC is unproven, because every closed list in this area looked
  open until someone tried."* Someone tried; this issue is the result.
* The failure mode is the bad kind. The scan produces a confident, correct,
  actionable answer (`root[1] (workspace)`, with shadowing reported) for a name
  that the very next step rejects as unknown. A user following the documented
  provision convention gets told their package was found and then that their
  backend does not exist.

## What would settle the remaining uncertainty

Whether the BOARD axis resolves through the scan was not established here —
39 provisions exist and `check-derived-descriptor-fields.py:461` gates their
spelling, but the resolution path was not traced. Tracing `nros ws
board-facts` / `board_facts.rs` to the point where a board name becomes a
directory would settle it, and would say whether this issue is one axis or two.

## Fix direction (not applied)

`resolve_rmw_in`, the sibling of `serdes_resolver.rs:175`, plus a dispatch that
takes its rows from the scan rather than from `OUT_DIR`. Note that alone is not
sufficient — see issue 1215 (the root `CMakeLists.txt` chain fatals on a name
the dispatch accepts) and issue 1216 (the dispatch outputs that would carry an
out-of-tree provider's link data are read by nothing).
