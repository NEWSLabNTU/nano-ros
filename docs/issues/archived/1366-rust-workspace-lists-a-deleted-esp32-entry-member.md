## Symptom

`just build-test-fixtures lane=native` does not complete on `main`. Measured
2026-09-13 in the box tree during phase-455 W5; the run stops in the rust
workspace, and every later row in that lane goes unbuilt.

`examples/workspaces/rust/Cargo.toml:29` lists

```toml
    "src/esp32_entry",
```

as a workspace member. The directory does not exist:

```
$ ls examples/workspaces/rust/src/esp32_entry
No such file or directory (os error 2)
```

A cargo workspace refuses to load when a listed member has no manifest, so the
failure is at MANIFEST PARSE — the same absorbing shape as issue 0463: nothing
in the workspace can be read, and the error names the missing path rather than
the reason it is listed.

## What that file actually is — the premise both fix candidates rested on is false

`examples/workspaces/rust/Cargo.toml` is **not tracked** and **not generated any
more**. It is the residue of a generator that no longer exists:

- The leaf's own `.gitignore` lists `/Cargo.toml`, with the reason in place
  since phase-383 W10.a ("the root manifest and root CMakeLists are GENERATED
  … committing either would put a generated member list under review").
- `check-workspace-root-build-files` (phase-445 W6) *refuses* a tracked one, and
  `check-no-tracked-workspace-roots` refuses it a second way.
- The emitter that wrote it — phase-383 W3.a's workspace emitter in
  `packages/cli/nros-cli-core/src/builder/cargo_root.rs` — was **deleted by
  phase-445 W5**. What is left in that file classifies a root and `retire()`s
  it: it deletes one carrying `# GENERATED by \`nros build\`` and REFUSES an
  authored one.

Measured on the host checkout 2026-09-20: the file is dated 2026-09-01, opens
with `# GENERATED by \`nros build\` (phase-383 W3.a) — DO NOT EDIT.`, and
`src/esp32_entry` sits at line 29 — the exact line this issue quotes. So the
file the symptom was measured against is **pre-phase-445 build output**, present
in every checkout that ran that builder and absent from a clone.

## The decision, and why it is neither of this issue's candidates

RFC-0098 **D9** already decided it: *a workspace has no root build file.* "No
`<ws>/Cargo.toml`, no `<ws>/CMakeLists.txt`: a workspace is a directory of
packages, like a colcon workspace… The cargo root is the generated entry itself,
`build/<coord>/<entry>/Cargo.toml` (its `Cargo.lock` beside it), reaching
`src/*` as PATH dependencies."

Against that:

- **Candidate 1, "drop the member line", has the right argument and no action.**
  Its stated condition — "correct if a generated entry is reached through the
  image's own generated manifest rather than as a member of the tracked
  workspace root" — is exactly D9, and exactly what phase-445 W5 implemented for
  `esp32_entry` (`[image.esp32]` generates it under `build/`). But there is no
  tracked member list to edit and no generated one to change: the whole file is
  retired output.
- **Candidate 2, "make the lane generate the entry first", is ruled out by the
  same decision.** A generated entry is a cargo ROOT; it is not a member of
  anything, so no amount of generating makes `src/esp32_entry` a legal member —
  the generator writes `build/<coord>/esp32_entry`, not `src/`. Coupling a
  native lane to an esp32 generation step would also buy nothing here.
- **The third answer, "generate the member list", is what the tree did until
  2026-09-11 and was deliberately undone.** D9 supersedes RFC-0065 D3's "the
  cargo root is `<ws>/Cargo.toml` and nowhere else" with a measurement: a root
  `[workspace]` above a generated entry makes cargo refuse the entry with
  `current package believes it's in a workspace when it's not`.

So the file is right not to exist, and the defect is that **nothing said so
before a build tripped over it**. `retire()` is the one sanctioned remover and
it runs at stage 4 of `plan_builds`, inside the `Driver::Cargo` arm, per image —
after stage 1 has read the stale root's member list
(`discover::cargo_members_or_walk`) and after anything earlier in a lane that
runs cargo in that directory. Everything in that window sees the broken
workspace and dies the way 0463 dies.

And the gate that owns the rule could not see the file at all:
`check-workspace-root-build-files` reads `git ls-files`, while the root that
breaks a build is precisely the gitignored one. A gate whose REACH is narrower
than the rule it enforces — CLAUDE.md's issue-0196 class, again.

## Reproduction of the mechanism

In the fresh box tree, with the host checkout's stale root copied in:

```
$ cd examples/workspaces/rust && cargo metadata --no-deps --format-version 1
error: failed to load manifest for workspace member
  `…/examples/workspaces/rust/build/freertos-zenoh/freertos_entry`
referenced by workspace at `…/examples/workspaces/rust/Cargo.toml`
Caused by:
  failed to read `…/build/freertos-zenoh/freertos_entry/Cargo.toml`
Caused by:
  No such file or directory (os error 2)
(exit 101)
```

Fourteen of that root's fifteen unresolvable members are `build/<coord>/<entry>`
paths a build in *that* tree would have produced. `src/esp32_entry` is the one
no tracked directory and no generator provides at all.

## Fix

`scripts/check-example-workspace-members.py`, wired as the fast-lane gate
`check-example-workspace-members` (`just check example-workspace-members`) — the
ON-DISK half of D9, beside the tracked half:

> If an `examples/workspaces/<ws>/` or `examples/templates/<ws>/` directory
> holds a `[workspace]` root manifest on disk, every path in its `members` must
> resolve to a directory with a `Cargo.toml`.

It reads the member list the way `builder/discover.rs` does (globs expanded,
`exclude` honoured, mid-path globs skipped), classifies each finding by what
could ever provide it (a tracked directory / `build/`, i.e. generator output /
nothing), and reads the manifest's first line to say whether the root is
GENERATED — retired build output, gitignored, deleted by `nros build` — or
AUTHORED, which D9 says should not exist either.

It is on `check::fast`, which is `build-test-fixtures`' first dependency, so a
checkout carrying the stale root now fails at the head of the lane naming the
file, instead of four frames into cargo somewhere in the middle of it.

**Zero manifests is the expected reading on a clean tree, and is reported as a
count** — because "examined nothing" is also what a wrong glob or a wrong repo
root would print. `self_test()` runs on the normal path with a control in both
directions: a well-formed workspace must pass, and the same tree plus one
phantom member must fail, naming the member.

### What the fresh clone needed, and what it did NOT

The clone needed ordinary provisioning before the lane could run at all —
`just setup-clang-format`, `nros setup --build-sources`, the `play_launch`
submodule plus a CLI rebuild, and `nros setup --source freertos-kernel`/`lwip`
for the `orch_tiers_freertos` COMPILE-CHECK fixture (compile-check fixtures are
built for every lane, unnarrowed). None of that is this issue, and none of it
touched the rust workspace.

It did NOT need an esp32 step, a member line, or a root manifest — which is the
claim under test.

phase-455's note says this "cannot complete from a clone". That half is not
reproducible and was never the defect: a clone has no root manifest, because the
root manifest is gitignored build output. The failure it measured needs a
checkout that had run the pre-phase-445 builder.


## What is not fixed here

`retire()` still runs at stage 4 rather than before discovery. That is a real
ordering (`nros build` heals the file only once it reaches the first cargo
image), but it is not load-bearing for this issue: the gate now stops the lane
before anything reads the workspace, and moving a call that DELETES a file
earlier in `plan_builds` would make it run for workspace shapes that never
reach the cargo driver. Worth its own issue if the window is ever measured to
bite something the gate does not cover.
