## What is left

[phase-440](../../roadmap/archived/phase-440-nros-store-is-the-root.md) was
archived on 2026-10-12. Its W7 (the per-project pin and dispatch by it) landed
with one acceptance clause named as still open.

**The claim:** "a pin bump re-stales generated code through #182". On the
contributor path, #182 keys regeneration on the CLI source stamp. On the user
path it would key on the toolchain version. That is the same machinery pointed
at a different input, but nothing tests it on the user side. phase-440 also says
that two projects building side by side need a real release asset.

**What already exists:** the user-path probe phase-440 W8 asked for has landed
as `just probe installed` (phase-447 A3). It builds the asset that
`release-nros.yml` would publish and runs `first-project.md` on a host with no
checkout. It does not bump a pin.

## What closes it

Extend the installed-path probe, or add a test beside it: build a `nros new`
project against pin A, bump the project's pin to B, rebuild, and assert that the
generated code was regenerated by B's codegen (by its codegen version, RFC-0090).
Two projects pinned to different versions on one host would cover the
side-by-side case too.

## Resolution (2026-10-23)

**Measured by reading the decision, and the claim was false.** Every road
decides "is `generated/` current" through one record,
`<generated pkg>/nros-generated.toml` (`rosidl_codegen::ament_stamp::Stamp`):
`nros build` (`moved_generated` / `refresh_generated` in `cmd/ws.rs`), and both
cmake generators through `nros codegen --ament-witness`. The record held
`{package, ament, codegen}`, where `codegen` is the `EMITTED_CODEGEN_VERSION`
integer. Nothing in it named the emitter that ran. The #182 machinery the claim
leaned on is a CONTRIBUTOR-side edge: an mtime on the tool path, and the CLI
source stamp, which on the user path go quiet (`stale_guard.rs` returns Ok with
no checkout). A pin edit does not move the front `$NROS_HOME/bin/nros` either.

So on the user path a pin bump from A to B regenerated only when B's codegen
VERSION differed from A's, or the ament inputs moved, or the user ran `nros
sync` (which always regenerates). Two releases carrying the same version (it is
18 in both `codegen_version.rs` arms today) and emitting different bytes: `nros
build` under B compiled A's output as current. This is a correctness defect,
not just an unmeasured claim, so the issue is retyped as a bug.

**Fix.** The record gains `emitter`, which is `codegen_fingerprint()`: the hash
of every byte this build of the emitters produces for the corpus, memoized per
process (~20 ms). A mismatch regenerates and names the reason ("generated by a
different emitter … at the same codegen version N"). A record without the field
predates it and regenerates once, reported as such rather than as unrecorded.
RFC-0104 D4/D5 are amended.

**Tests, one per road, each with a negative control:**

- `rosidl-codegen` `ament_stamp`:
  `a_different_emitter_at_the_same_codegen_version_is_a_move`,
  `a_record_without_an_emitter_reads_as_moved`.
- cargo road, `nros-cli-core` `cmd::ws`:
  `a_crate_generated_by_another_toolchain_is_reported`. A workspace left exactly
  as `nros sync` leaves it, with its record re-stamped by another emitter, is
  reported moved; its own record is current.
- cmake road, `cargo-nano-ros` `ament_witness_tests`:
  `output_from_another_emitter_regenerates_at_configure`.

**Not measured, and named:** the whole chain through two real release assets,
with the front dispatching by pin and cmake's configure reaching the pinned
binary. The decision is tested; the hand-over is covered by
`toolchain_dispatch.rs`. Two projects pinned side by side still needs a real
release asset, as phase-440 said.
