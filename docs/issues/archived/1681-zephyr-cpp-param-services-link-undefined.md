## What

Measured 2026-10-04 on a TEMPORARY image of `examples/workspaces/cpp`
(`zephyr_svc`: native_sim, zenoh, the service server's node, `[system]
features = ["param_services"]`), built through `nros build zephyr_svc -- -d
<dir>` in a worktree-local Zephyr workspace:

```
.../build/m1649-west/zephyr_svc_entry_nros_main_generated.cpp:37: undefined reference to `nros_cpp_register_parameter_services'
```

The generated entry calls `nros_cpp_register_parameter_services(executor)`
because the bringup declares `param_services` (that is the codegen rule pinned
by `codegen/entry/emit/tests_c.rs`). The symbol is defined in
`packages/api/nros-cpp/src/params_shim.rs` under nros-cpp's `param-services`
feature. `zephyr/CMakeLists.txt` appends `,alloc,param-services` to the nros-cpp
feature list when `"param_services" IN_LIST NANO_ROS_FEATURES`, so either that
list does not hold the bringup's features on this road, or the archive that is
linked is not the one built with them. Not diagnosed further: it was found
while measuring issue 1649, whose build-script outputs are produced before the
link and were diffed regardless.

## Reproduce

Add an image to `examples/workspaces/cpp/src/demo_bringup/system.toml` with
`board = "native_sim"`, `rmw = "zenoh"`, a launch file running the service
server, and `features = ["param_services"]`; `nros sync`; `nros build <image>`.

## Acceptance

That image links; a fixture row or a `check-compile-smoke`-tier build holds it,
because no in-tree Zephyr C++ image declares `param_services` today, which is
why nothing caught this.

## Resolution (2026-10-05)

**Root cause: the generated west application never stated the capability
axes.** `zephyr/CMakeLists.txt` reads `NANO_ROS_FEATURES` while
`find_package(Zephyr)` runs, to pick nros-cpp's cargo features and the
`NROS_SYSTEM_*` defines. On the cmake road `nano_ros_workspace(SYSTEM ...)` sets
it before the import (issue 0353). On the west road the application is
generated by `builder::west_app::render_cmake_app` (phase-470 W5.b3), and it set
nothing. So nros-cpp was built `,alloc,param-store` and never `param-services`,
while the generated entry, which reads the axes from the model, called
`nros_cpp_register_parameter_services`. The archive linked was the right one;
the feature list was empty. The module's own comment at the
`param_services IN_LIST NANO_ROS_FEATURES` site had already named this gap:
"Follow-up: resolve from the entry's BRINGUP" (issue 0745).

**A second instance of the class, measured while proving the first:**

- The Zephyr module mapped `param_services` and no other axis. The cmake road
  maps every axis through `nros_feature_set`.
- `features`'s bringup declares `lifecycle` too. Once the first fix was in,
  the C++ image there failed with `undefined reference to
  nros_cpp_lifecycle_autostart`.

**Fix.**

1. `CmakeApp.features`: the bringup's axes, read with
   `cmd::build::declared_capabilities`, which uses `capability_enabled` over
   the registry, so `[system] features` and the deprecated typed blocks both
   count.
   - `render_cmake_app` emits `set(NANO_ROS_FEATURES "<a>;<b>")` before
     `find_package(Zephyr)`.
   - A bringup with no axis gets no line.
2. `zephyr/CMakeLists.txt` maps the two remaining axes through a new
   `_nros_cap_suffix`:
   - `lifecycle` becomes `lifecycle-services`.
   - `safety` becomes `safety-e2e`, on zenoh only, matching the cmake road's
     backend condition, with a warning otherwise.
   - The suffix is appended to the nros-cpp string and to BOTH nros-c strings
     (C-API and C-for-C++), because nros-cpp forwards both features to nros-c
     and a feature reaching one unit only is issue 1100's split.
   - `NanoRosCapabilities.cmake`'s stale "lifecycle-services is always
     compiled in" comment now says where the feature is actually chosen.

**Measured.**

- **Original repro.** The issue's temporary `[image.zephyr_svc]` on
  `examples/workspaces/cpp` (native_sim, zenoh, the service server,
  `features = ["param_services"]`), built through `nros build ...
  --zephyr-workspace <worktree-local cp -al workspace>`:
  - The generated `CMakeLists.txt` carries `set(NANO_ROS_FEATURES
    "param_services")`.
  - nros-cpp builds with
    `rmw-zenoh-cffi,platform-zephyr,ros-humble,std,alloc,param-services`.
  - The image LINKS.
- **Negative control.** Deleting that one generated line and re-running ninja
  in the same build dir reproduces the issue's error verbatim:
  `zephyr_svc_entry_nros_main_generated.cpp:37: undefined reference to
  'nros_cpp_register_parameter_services'`. Restoring it links again.
- **Boot, original repro.** Against `rmw_zenohd` with the default 64 KiB
  `NROS_ZEPHYR_HEAP_SIZE`, it halts registering the services:
  `HEAP EXHAUSTED: request 285696 bytes, arena 66048`. That is issue 1677's
  allocation on a conf 1677 did not touch, filed as **issue 1702**.
- **Boot, raised heap.** With `CONFIG_NROS_ZEPHYR_HEAP_SIZE=524288` and a
  launch `<param name="probe_rate" value="5"/>`:
  - `ros2 node list` shows `/add_server`.
  - `ros2 service list` shows the six `/add_server/*_parameters` services.
  - `ros2 param list` shows `/add_server: probe_rate`.
  - `ros2 param get /add_server probe_rate` returns `Integer value is: 5`.
- **The permanent image.** New `[image.zephyr_cpp_params]` in
  `examples/workspaces/features`, which declares `param_services` and
  `lifecycle`. It uses the shared `prj-zenoh.conf` (512 KiB heap) plus a new
  `prj-cpp.conf` that turns the shared Rust `prj.conf` into a C/C++ image.
  - Before the zephyr/CMakeLists half: `undefined reference to
    nros_cpp_lifecycle_autostart`.
  - After: it links with
    `...,alloc,param-services,lifecycle-services,...`.
  - Against `rmw_zenohd`: `ros2 param list` shows `/param_talker:
    publish_period_ms`, `ros2 param get` returns `Integer value is: 250`,
    `ros2 param describe` reports `Type: integer`, and the image logs
    `Published: 250`, the live-read value.

**What holds it now.** The acceptance asked for a fixture row; this goes as
far as a runtime cell.

- Fixture row `workspace-zephyr-cpp-params`:
  - west build dir `build-ws-cpp-params-entry-zenoh`
  - locator `port_of(ZephyrNativeSim, Cpp, Params)` = 7670
- Matrix cell `ZephyrNativeSim/Cpp/Zenoh/Params/Workspace`, claimed by
  `entry_e2e`. Its proof is the C++ native params cell's: `int32-sink` sees
  `Received: 250` three times.
- Built with `NROS_ZEPHYR_FIXTURE_FILTER=build-ws-cpp-params just build
  zephyr` and run with `cargo nextest run -p nros-tests --test entry_e2e -E
  'test(entry_matrix)'`: `entry_matrix: 1 ran, 17 skipped, 0 failed`. The cell
  that ran is this one; the 17 skips are other platforms' unbuilt fixtures.
- Unit test
  `west_app::tests::the_capability_axes_are_set_before_find_package_zephyr`
  pins the generated line, its position, both axis spellings, and its absence
  when nothing is declared.

The census prepass of that build first failed on
`derived-tiers-cpp`'s native census (`dump ... failed (rc=-2)`, exit 156).
That is issue 1693, already open and unrelated. The fixture build above ran
with `NROS_CENSUS_PREPASS=done`, since this row's model has no contract.
