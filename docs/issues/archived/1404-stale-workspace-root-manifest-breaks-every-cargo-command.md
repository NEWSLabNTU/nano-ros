## Symptom

Any cargo command run from any package in `examples/workspaces/rust` fails
before doing anything:

```
error: failed to load manifest for workspace member
  `…/examples/workspaces/rust/src/esp32_entry`
referenced by workspace at `…/examples/workspaces/rust/Cargo.toml`
Caused by: failed to read `…/src/esp32_entry/Cargo.toml`
Caused by: No such file or directory (os error 2)
```

It is not a formatting nuisance. It **fails the native fixture lane**:

```
build-test-fixtures: lane=native
  777:   0: cargo metadata at "…/examples/workspaces/rust/Cargo.toml":
         failed to load manifest for workspace member `…/src/esp32_entry`
error: Recipe `build-workspace-fixtures` failed on line 259 with exit code 2
```

so tier 1 is unreachable, and `just format` dies on the same file — which
matters in its own right, because formatting has to precede a fixture build or
every native fixture re-stales.

## Cause, measured — and NOT what this issue first said

The file's own header says what it is:

```
# GENERATED by `nros build` (phase-383 W3.a) — DO NOT EDIT.
# Regenerated on every build from the packages discovered in the workspace.
```

mtime **2026-09-03 17:51**, untracked, eighteen days old. It lists
`src/esp32_entry` because in the pre-RFC-0098 layout there was a hand-written
package at that path. RFC-0098 D9 moved generated entries to `build/<coord>/`
and removed the workspace root manifest entirely — `builder/entry.rs` says so in
its own comment: *"There is no `<ws>/Cargo.toml` any more."*

**Measured:** `nros build native` in that workspace **deletes the file** and the
build succeeds. So the current builder is correct and the file is residue of a
generation that predates it.

`nros sync` does not manage this file, so a tree that syncs without building
that particular workspace keeps the broken manifest indefinitely — which is the
state `build-test-fixtures` walks into, because it reaches `cargo metadata`
before it reaches a build of that workspace.

**The first version of this issue blamed `nros sync` for emitting the member.**
That was wrong. The evidence that produced it was real — removing
`src/esp32_entry/` and re-running `nros sync` left the member in place — but the
conclusion did not follow: nothing rewrote the file, because sync never writes
it at all. A confident wrong root cause is worse than an open question, so it is
recorded here rather than quietly replaced.

## The residue is one family, not two

`examples/workspaces/rust/src/esp32_entry/` still exists on disk, untracked,
containing exactly one file:

```
src/esp32_entry/.cargo/config.toml
  include = [ "../../../../../../nros-patch.toml", "nros-board.toml" ]
```

`nros-board.toml` is the board projection phase-445 W6 deleted (RFC-0098 D1).
So the directory and the root manifest are leftovers of the **same** superseded
layout — the manifest names the package, the package's `.cargo` names the
projection, and all three died with RFC-0098. It is not a coincidence sitting
next to a bug; it is the same residue.

## Scope

One workspace, measured across all fifteen:

```sh
for w in examples/workspaces/*/; do [ -f "$w/Cargo.toml" ] && stat -c '%y %n' "$w/Cargo.toml"; done
```

`examples/workspaces/rust` (now repaired by `nros build native`) and
`examples/workspaces/safety` (2026-09-03 18:16, equally stale, but every member
it names still exists, so it is inert rather than fatal). The other thirteen
have none.

## What would fix it

The builder already removes the file when it runs. What is missing is anything
that notices it when the builder does NOT run:

* `nros sync` should delete a workspace-root `Cargo.toml` it finds, or refuse
  with the reason — sync is what every lane runs first, and it is where the
  file's absence could be made true cheaply.
* Or `check-workspace-root-build-files`, which today forbids a **tracked**
  workspace-root manifest, should also report an untracked one. The tracked rule
  protects a clone; it says nothing about the machine that has been here since
  before RFC-0098, which is where the failure actually happens.

The second is the smaller change and catches the `safety` one too, which is
currently inert only by luck.

## Acceptance

* A stale workspace-root `Cargo.toml` is reported, or removed, without needing a
  successful `nros build` of that workspace first.
* The failure names the file, rather than surfacing as `cargo metadata` failing
  for an unrelated package 700 lines into a fixture-build log.
* `examples/workspaces/rust/src/esp32_entry/` and
  `examples/workspaces/safety/Cargo.toml` are gone.

## Fix

The second remedy, as argued above: `check-workspace-root-build-files` now
reports an UNTRACKED workspace-root build file as well as a tracked one. The
rule did not change — only its reach, which was narrower than the rule it
enforces (the issue-0196 shape). The tracked arm protects a clone; the untracked
arm is about the machine where the failure actually happens.

`untracked_offenders()` walks the immediate children of `examples/workspaces`
and `examples/templates` and stats two names in each — about sixty stats, and it
never descends. That matters: `examples/**` is full of untracked generated
trees, and a gate that walked them would report a `build/<coord>/<entry>/
Cargo.toml`, which is the root `nros build` is SUPPOSED to write. A path that is
tracked is left to the tracked arm, so one file never produces two findings with
two different remedies. The exemption is still the SHAPE — a `package.xml` at
the root — and it is now read from the index **and** from disk, so an untracked
single-package leaf is exempt on the machine that has it.

The message for an untracked finding says what a tracked one cannot: the file is
in no commit, a clone does not have it, and the remedy is `rm` (or `nros build`,
which deletes it) rather than a change to a commit.

### Selftest

Six cases, in the gate's own `self_test()` which runs on the normal path:

* the untracked arm is EMPTY while only tracked roots exist — without this,
  every case below could pass by re-reporting the tracked findings;
* the 1404 shape itself: a root manifest on disk, in no commit, is found;
* a member manifest at `src/<pkg>/` and a generated entry at
  `build/<img>/<entry>/` are NOT found — the false-positive direction;
* an untracked single-package leaf with a `package.xml` is exempt, and the same
  leaf without one is a finding, so the exemption is measured;
* a tracked root is reported once, by the tracked arm.

Mutation-tested: an arm that returns `[]`, an arm that walks recursively, and an
arm that drops the shape exemption are each caught by these cases. Verified
against the pre-fix gate on a reproduction of the exact defect
(`examples/workspaces/rust/Cargo.toml` naming `src/esp32_entry`): the old gate
prints `OK (no tracked root …)`, the new one names the file.

## What is left, and why it is not in a commit

`examples/workspaces/rust/src/esp32_entry/` — a directory whose only content is
a `.cargo/config.toml` including the `nros-board.toml` that phase-445 W6
deleted — still exists on the developer machine where this was measured. It is
untracked residue of one checkout: no clone has it, nothing in the tree
references it, and a commit cannot remove it. `rm -rf
examples/workspaces/rust/src/esp32_entry` is the whole of it. It is recorded
here rather than left implicit because it is the other half of the same
superseded layout, and because the file that made it FATAL — the root manifest
naming it — is what this gate now catches.

Note for whoever touches this next: the tracked half of this rule is enforced
TWICE, by this gate and by `check-no-tracked-workspace-roots` (phase-383 W10.c).
Neither covered the untracked half; the arm landed here, once, rather than in
both, so a finding is reported once.
