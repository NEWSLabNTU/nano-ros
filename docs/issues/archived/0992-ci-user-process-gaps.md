## The intended shape

The workflow is meant to read as a transcript of a user session (phase-411 W4),
against a ROS 2 vocabulary a user already has:

| ROS 2 | nano-ros | does what |
| --- | --- | --- |
| `rosdep install` | `just setup <scope>` | provision dependencies |
| `colcon build` | `just build <scope>` | **codegen** + build |
| — | `just test <scope>` | run |

The middle row is where this broke. `colcon build` generates messages; that is
why a ROS user never types a separate codegen command. Our equivalent has the
codegen stage — `scripts/regenerate-bindings.sh`, behind `just generate-bindings`
— but only some of the paths into `just build` ran it.

## Gap 1 — codegen was reachable from one build lane and not the other

`build-test-fixtures` listed the generators itself, so the scoped fixture path
was fine. `rust-rtos-link-check` listed only the preflight:

```
rust-rtos-link-check: _require-leaf-includes
```

`_require-leaf-includes` (issue 0463) asserts that codegen has **already** run:
it fails when a tracked leaf `.cargo/config.toml` reaches a gitignored,
sync-generated `include` target. As a dependency with no generator in front of
it, on a fresh checkout it is unsatisfiable — the only thing that would satisfy
it is downstream of itself.

That is the lane `build-wide` runs. `just ci matrix build` → `_matrix-build` →
`l3` → `rust-rtos-link-check`, and every run ended:

```
error: 54 unresolved `include` target(s) across 54 of 73 tracked
       .cargo/config.toml files.
  examples/qemu-arm-baremetal/rust/listener/.cargo/config.toml
      include -> ../../../../../nros-patch.toml  (absent)
These targets are gitignored and generated by `nros sync`; a clone never has them.
```

The preflight itself is right — 0463 added it precisely so cargo's
manifest-parse error stops being four frames deep with no mention of sync. What
was wrong is that this lane never performed the step it names.

**It is invisible on a developer machine**, which is why it survived: a
developer's leaves were synced by some earlier run, so the dependency passes and
the ordering never shows. It is unsatisfiable only on a fresh checkout — the
third instance this week of "developer-machine residue satisfies a precondition
CI can never satisfy", after the `activate.sh` PATH race (#200) and the stale
in-tree CLI.

### Gap 1b — the other lane had the two steps in the wrong order

`build-test-fixtures` did list both generators, but like this:

```
… _clear-fixture-stamp generate-bindings setup-launch-resolve build-zenoh-posix-fixture …
```

Dependencies run left to right, so codegen ran **before** the helper it needs was
built. `nros sync` refuses to resolve a SystemModel without `nros-launch-resolve`
— it errors rather than reusing a museum model (issue 0409) — so on a tree that
lacks the binary, codegen dies naming a helper the very next dependency would
have built. Reproduced in a detached worktree:

```
Error: sync: 1 SystemModel(s) need resolving but `nros-launch-resolve` is not
next to the `nros` binary:
  demo_bringup — …/examples/templates/c-and-cpp-mixed-workspace/build/nros/models/…
```

Same shape as Gap 1, one step earlier: a mandatory step ordered after the step
that consumes it, invisible wherever the artifact already existed.

## Gap 2 — 5 of 8 workflows never adopted the process

Only three lanes are written as `setup <scope>` then one command:

| workflow | shape |
| --- | --- |
| `build-wide.yml` | `just setup tier2` → `just ci matrix build` |
| `run-matrix.yml` | `just setup tier2` → `just ci matrix` |
| `nightly.yml` (`matrix-nightly`) | `just setup tier2-nightly` → `just ci matrix-nightly` |

The rest still hand-roll provisioning that phase-411 W4 said `just setup <scope>`
absorbs:

* **`host-tests.yml`** — `nros setup --source` with six flags, three
  `nros setup --tool …` invocations (one with a hand-built `--prefix`),
  `just ci provision-zenohd`, and `just setup-launch-resolve`. Nine provisioning
  steps, none of them a user verb.
* **`nightly.yml`** `platform` and the three `zephyr-*` jobs — `nros setup
  --source …` plus `just setup-launch-resolve` per job.

A reader comparing these to the book cannot answer "does CI do what I do?",
which is the property the transcript shape exists to give.

**Still open.**

## Gap 3 — `just setup <scope>` provisioned less than `just setup <tier>`

An earlier draft of this issue said `setup-launch-resolve` was not in the `setup`
recipe at all (`grep`: 0 hits). That was wrong, and the truth is worse, because
it is invisible to grep: it **was** there, on the tier path only. Both the
PRESET arm (`just setup tier2`) and the PLATFORM arm (`just setup zephyr`)
`exit 0` / `exec` several dozen lines earlier, so the one spelling phase-411 W4
tells every CI job to use provisioned the CLI and nothing else.

So `build-wide`, whose provisioning step is exactly `just setup tier2`, could not
have had the resolver even once Gap 1 was fixed.

`just ci provision-zenohd` is still unreachable from `just setup`. **That half
stays open.**

## The fix

* A named codegen stage, `_codegen`, in the order the steps actually depend on
  each other: `setup-launch-resolve` → `generate-bindings` → the 0463 preflight
  as a **verification** of the tree codegen just produced, rather than a
  precondition nothing satisfies.
* Both build lanes depend on it (`build-test-fixtures`, `rust-rtos-link-check`),
  and `just build` runs it for **every** scope — previously only the unscoped
  path did, so `just build <scope>`, the spelling every CI job uses, built
  against whatever `generated/` the tree happened to carry.
* A `_setup-common` preamble every `just setup` arm runs: the guarded,
  non-recursive `play_launch` submodule init that `bootstrap.sh` already does
  for `base`, then `setup-cli`, then `setup-launch-resolve`.

## Why this was worth fixing as one thing

Each gap alone reads as a workflow detail. Together they are one fact: **the
chain a user is told to run was not the chain CI ran, and the difference is
exactly where CI kept failing.** Three separate reds this week (`runner-doctor`,
the CLI PATH race, and this include preflight) were all found only after a lane
that had never run started running, because no developer path exercises the
fresh-checkout ordering.
