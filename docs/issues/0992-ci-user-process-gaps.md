## The intended shape

The workflow is meant to read as a transcript of a user session (phase-411 W4),
against a ROS 2 vocabulary a user already has:

| ROS 2 | nano-ros | does what |
| --- | --- | --- |
| `rosdep install` | `just setup <scope>` | provision dependencies |
| `colcon build` | `nros build` / `just build <scope>` | **codegen** + build |
| — | `just test <scope>` | run |

The middle row is where this breaks. `colcon build` generates messages; that is
why a ROS user never types a separate codegen command. nano-ros's equivalent
step does not.

## Gap 1 — codegen has no home, and its preflight is circular

`nros build` does not sync. It names `nros sync` in two error strings and never
runs it (`cmd/build.rs:952`, `:1828`). There is no `just sync` verb either —
`just --list | grep sync` is empty. So the codegen stage exists, is mandatory,
and is not reachable from any verb in the documented chain.

`just build <scope>` *does* sync, per leaf, inside `fixtures-build.sh:432`. But:

```
build-test-fixtures-leaves lane="all": _require-leaf-includes
```

`_require-leaf-includes` is a **dependency**, so `just` runs it before the body
— and the body is what reaches the sync. On a fresh clone the preflight cannot
pass, because the only thing that would satisfy it is downstream of itself.

That is not theoretical. `build-wide` fails on it every run:

```
error: 54 unresolved `include` target(s) across 54 of 73 tracked
       .cargo/config.toml files.
  examples/qemu-arm-baremetal/rust/listener/.cargo/config.toml
      include -> ../../../../../nros-patch.toml  (absent)
These targets are gitignored and generated by `nros sync`; a clone never has them.
```

The preflight itself is right — issue 0463 added it precisely so cargo's
manifest-parse error stops being four frames deep with no mention of sync. What
is wrong is that nothing in the chain performs the step it names.

**It is invisible on a developer machine**, which is why it survived: a
developer's leaves were synced by some earlier run, so the dependency passes and
the ordering never shows. It is unsatisfiable only on a fresh checkout — the
third instance this week of "developer-machine residue satisfies a precondition
CI can never satisfy", after the `activate.sh` PATH race (#200) and the stale
in-tree CLI.

Two candidate fixes, and they are not equivalent:

* **Put codegen in the build verb**, matching `colcon build`. Then
  `setup → build → test` is complete and the preflight becomes a diagnostic for
  a user who ran `cargo` directly rather than a gate the chain trips over.
* **Narrow the preflight to the leaves in scope.** Cheaper, but it keeps codegen
  as an unnamed fourth step, which is the thing the ROS analogy exists to avoid.

## Gap 2 — 5 of 8 workflows never adopted the process

Only three lanes are written as `setup <scope>` then one command:

| workflow | shape |
| --- | --- |
| `build-wide.yml` | `just setup tier2` → `just ci matrix build` |
| `run-matrix.yml` | `just setup tier2` → `just ci matrix` |
| `nightly.yml` (`matrix-nightly`) | `just setup tier2-nightly` → `just ci matrix-nightly` |

The rest still hand-roll provisioning that phase-411 W4 said `just setup <scope>`
absorbs:

* **`host-tests.yml`** — `nros setup --source` with six flags, three
  `nros setup --tool …` invocations (one with a hand-built `--prefix`),
  `just ci provision-zenohd`, and `just setup-launch-resolve`. Nine provisioning
  steps, none of them a user verb.
* **`nightly.yml`** `platform` and the three `zephyr-*` jobs — `nros setup
  --source …` plus `just setup-launch-resolve` per job.

A reader comparing these to the book cannot answer "does CI do what I do?",
which is the property the transcript shape exists to give.

## Gap 3 — provisioning verbs that `just setup` cannot reach

Both of these are provisioning, and neither is reachable from `just setup`:

* `just setup-launch-resolve` — a separate step in **five** jobs. `grep` of the
  `setup` recipe for it: 0 hits.
* `just ci provision-zenohd` — provisioning under the `ci` verb. 0 hits in
  `setup`.

So a user who follows the documented chain provisions neither, and every lane
that needs them re-adds them by hand. That is the same "two spellings of one
fact" that `runner-provision.sh` refuses to introduce for runners ("a second
installation path is how a runner ends up with a subtly different toolchain
from every developer").

## Why this is worth fixing as one thing

Each gap alone reads as a workflow detail. Together they are one fact: **the
chain a user is told to run is not the chain CI runs, and the difference is
exactly where CI keeps failing.** Three separate reds this week
(`runner-doctor`, the CLI PATH race, and now the include preflight) were all
found only after a lane that had never run start running, because no developer
path exercises the fresh-checkout ordering.
