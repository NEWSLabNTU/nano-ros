# Phase 581 - ROS 2 environment variables against system.toml

**Status (2026-11-19). Draft, planned: design in review; no item started.**
Implements [RFC-0140](../design/0140-ros-env-vars.md): every environment
variable a nano-ros process reads gets one disposition (RESPECT, IGNORE,
REFUSE) from one registry, read through one reader shared by C, C++ and Rust;
an environment value that overrides what `system.toml` states is warned once,
and an ignored variable is reported once.

The user ruled on RFC-0140's open questions on 2026-11-19: Q2 to Q11 are
decided (RFC-0140 "Decisions"); Q1 is reopened, because environment
variables are to join the knob registry under one naming scheme and board and
RMW packages are to declare their own rows. So W1 (the registry) and W2 (the
reader) wait for the revised Q1 design; W0's measurements do not. Each item is one
PR, claimed with `just claim phase-581-wN`.

## Why

The user ruled for `ROS_DOMAIN_ID` on Linux: the stated value is respected,
the environment overrides it, a mismatch is warned. Issue 2714 (PR #4285)
implemented that for the domain and the locator. RFC-0140's inventory found
the rest unruled: nano-ros reads environment variables in at least eleven
runtime files through their own readers, two road gaps go unreported (six
`ZENOH_*` variables are Rust-only; `freertos-posix` reads the environment on
its C/C++ road but not its Rust road), and no standard ROS 2 variable except
`ROS_DOMAIN_ID` is either honoured or reported as ignored.

## Work items

### W0 - Re-measure the inventory on a running image

- **Status:** OPEN
- RFC-0140's inventory was measured by reading code. Run it: a Linux image
  per road (Rust, C, C++) and a `native_sim` image, each variable set, and
  record whether the process acted on it. Settles RFC-0140 Q8 (`native_sim`)
  and Q11 (`freertos-posix` Rust).
- **Acceptance:** the inventory table in RFC-0140 carries a "measured" mark
  per row, and any row the run contradicts is corrected in the same PR.

### W1 - The registry

- **Status:** OPEN
- The `[[env]]` rows (RFC-0140 D4) in the place Q1 rules, generated by
  `scripts/gen-knob-registry.py` into a Rust table, a C header and the book's
  reference table. One row per variable in RFC-0140's inventory, with its
  disposition, its statement, its parse rule and its readers.
- **Acceptance:** the generator's staleness check (`just check
  knob-registry`) covers the new rows; a row whose `stated` key is not a
  `system.toml` key the CLI's schema knows fails generation.

### W2 - The shared reader, `nros-env`

- **Status:** OPEN
- The `#![no_std]` crate of RFC-0140 D4: `get`, `resolve`, `notice_if_set`,
  `refuse_if_set`, the once-per-row bitset, the startup sweep, and the C ABI
  plus `<nros/env.h>`. `nros::env` keeps its ladder and `report` and builds
  its `EnvRung` from `nros-env`; issue 2714's
  `env_overrides_statement`/`warn_env_overrides_statement` become per-row
  calls with unchanged output.
- **Acceptance:** issue 2714's `host_connect_facts` test passes unchanged;
  a unit test resolves one row twice in one process and observes one warning;
  a freestanding build of `<nros/env.h>` returns NULL without linking
  `getenv`.

### W3 - The gate `env-reads-through-registry`

- **Status:** OPEN
- RFC-0140 D5's four rules, as a test in `packages/testing/nros-gates`, on
  the fast line, with a ratchet baseline listing today's bypassing reads so
  it lands green and only falls.
- **Acceptance:** the self-test plants a bypassing `getenv` in a temporary
  tree and the gate names its file and variable; adding a new
  `std::env::var("NROS_X")` in a runtime crate fails the gate.

### W4 - Batch 1: the identity rows

- **Status:** OPEN
- Move `ROS_DOMAIN_ID`, `NROS_LOCATOR`, `NROS_RMW`, `NROS_NODE_NAME`,
  `NROS_NODE_NAMESPACE` and `NROS_SESSION_MODE` onto the registry, adding
  the mismatch warning for the four that issue 2714 did not cover. Close the
  `freertos-posix` Rust gap if Q11 rules so.
- **Acceptance:** for each of the six, a test in the `host_connect_facts`
  style, on Rust, C and C++ images: with the env unset the stated value is
  used; with it set the env value is used; the warning appears exactly when
  both are set and differ, and once.

### W5 - Batch 2: the middleware files

- **Status:** OPEN
- `ZENOH_SESSION_CONFIG_URI`, `CYCLONEDDS_URI` (compare and report only; the
  value stays Cyclone's to read), and the six nano-ros `ZENOH_*` variables,
  read through `nros-env` on both roads or retired, per Q4.
  `NROS_BRIDGE_<N>_LOCATOR`/`_DOMAIN` against `[[domain]]`.
- **Acceptance:** a C/C++ Linux image acts on each RESPECT row it did not

  file; the Cyclone warning says the two compose.

### W6 - Batch 3: the IGNORE and REFUSE rows

- **Status:** OPEN
- The notices for `ROS_LOCALHOST_ONLY`, `ROS_AUTOMATIC_DISCOVERY_RANGE`,
  `ROS_STATIC_PEERS`, `RMW_IMPLEMENTATION` (only when it maps to another
  backend), `ROS_NAMESPACE`, `ROS_LOG_DIR`, `ROS_HOME`, the `RCUTILS_*` rows,
  `ROS_DISABLE_LOANED_MESSAGES`, `ZENOH_CONFIG_OVERRIDE` and the non-enforced
  `ROS_SECURITY_*` rows; the refusal for `ROS_SECURITY_ENABLE` with
  `ROS_SECURITY_STRATEGY=Enforce`; the retired `ZENOH_LOCATOR`/`ZENOH_MODE`

- **Acceptance:** per IGNORE row, a test that sets it, boots an image with
  two sessions, and finds the notice exactly once; with
  `RMW_IMPLEMENTATION=rmw_zenoh_cpp` on a zenoh image, no notice; per REFUSE
  row, the boot fails naming the row and its replacement.

### W8 - Embedded: the build-time note

### W9 - Docs

- **Acceptance:** the book's docs gates pass; every registry row appears in

## Acceptance for the phase

- Every runtime environment read in the tree goes through `nros-env`, and
  W3's gate holds it there.
- Every variable in RFC-0140's inventory has a disposition, a test, and a row
  in the book.
- A user who sets any listed variable either sees it take effect (and, if it
  disagrees with `system.toml`, a warning) or sees one line saying it does
  nothing and what to use instead. On an embedded image the build says so.
