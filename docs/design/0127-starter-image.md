# RFC-0127 — One starter image, derived per audience

**Status:** Draft (2026-11-11). Records the decision SHAPE only. Nothing here
is ruled: every decision below is OPEN, with the recommendation stated, and
the open questions (Q1 to Q9) are the user's. The work is
[phase-551](../roadmap/phase-551-starter-image.md), which supersedes
[phase-523](../roadmap/phase-523-education-labs-adoption-probes.md) W2 (the
instructor image).

## Summary

Phase-523 W2 asked for an *instructor* image: the course toolchain, published
with the release, so installing a lab seat is a pull. The user has widened the
goal: a general **starter** image for newcomers, people who want a working
setup, educators and customers. One base, derived per audience or customer;
only one or a few images.

The proposal is one generator that writes one multi-stage Dockerfile, with
three targets: `host` (shared with the CI runner), `starter`, and
`starter-zephyr`. Audiences differ by RECIPE (how the image is started and
pinned), not by image. A customer derives their own image `FROM` ours under
written guarantees. The image is built and published by the release, and an
`image` probe track gates the moving tag.

## Problem

What exists today, read from the tree:

- **Three image sources, no starter.** `scripts/ci/runner-container.sh`
  generates `ci/docker/runner/Dockerfile` (`FROM ubuntu:22.04`, "Generated by
  scripts/ci/runner-container.sh — edit that, not this") from
  `nros-sdk-index.toml`. Beside it are two hand-written CI images,
  `ci/docker/ci-base/Dockerfile` and `ci/docker/zephyr-ros/Dockerfile`, each
  `FROM ros:humble-ros-base`, which `images.yml` publishes as
  `ghcr.io/newslabntu/nano-ros-ci` and `ghcr.io/newslabntu/nano-ros-zephyr-ci`.
  None of them is meant for a user, and the two hand-written ones are
  siblings that share nothing (`ci-base/Dockerfile`'s own header says so).
- **The runner image bakes no store, on purpose.**
  `scripts/ci/runner-container.sh:544-551` prints that the image "carries the
  RUNNER, not the toolchain and not this checkout", because baking the store
  "would go stale the moment nros-sdk-index.toml moves, with nothing to say
  so". A starter image must bake it: a pull IS the install. So the starter
  image needs a different rule for staleness (D5's guarantee 2).
- **The release asset has a floor of Ubuntu 22.04.**
  `scripts/probe/run-bootstrap-probe.sh:80-83`: `nros-launch-resolve` links
  `libpython3.10.so.1.0`, which 24.04 does not ship. So the image's base is
  22.04 (and therefore ROS 2 Humble) unless the asset gains a 24.04 build.
- **amd64 only.** `.github/workflows/release-nros.yml:98-100`: "Linux x86_64
  only for now … linux-arm64 waits on a runner decision — it is one matrix
  row when that is made, and the index already has the host key for it."
- **No dev container.** The tree has no `devcontainer.json`
  (`git ls-files | grep -ci devcontainer` is 0), so a course has no way to
  name the image a seat opens in.
- **`nros doctor` reports no container.** Its digests are of the firmware
  images `nros run` last started (`cmd/doctor.rs`), not of the container it
  runs in.

Phase-523 W2's measured sizes (uncompressed, provisioned host): the ROS base
758 MB (Humble), arm-none-eabi-gcc 1.2 GB, QEMU 486 MB, the FreeRTOS/lwIP/
zenoh-pico/mbedTLS sources 77 MB, a minimal Rust about 1 GB (not measured),
the Zephyr SDK 7.8 GB and its allowlisted workspace 1.7 GB. The current labs
run on `mps2-an385-freertos` and `mps2-an385-baremetal`; none needs Zephyr.

## Design (proposed shape, not ruled)

### D1 — One generator, one multi-stage Dockerfile (OPEN, Q7)

**Recommended (option B):** refactor `scripts/ci/runner-container.sh` into a
shared library that writes ONE multi-stage Dockerfile from
`nros-sdk-index.toml`, with targets:

- `host`: `ubuntu:22.04` plus ROS 2 Humble and the host packages the index
  names. Shared with the CI runner, so the image a user starts from and the
  one CI tests in are the same layers.
- `starter`: `host` plus the release `nros` (installed by `scripts/install.sh`,
  the user's own road), a baked `nros setup` for the Linux host and the
  `mps2-an385-baremetal` / `mps2-an385-freertos` boards with zenoh, a minimal
  Rust, and the template crates pre-warmed (D2).
- `starter-zephyr`: `starter` plus the Zephyr SDK and workspace (D3).

Alternatives: (A) a fourth hand-written Dockerfile for the starter, which
repeats the index in a file nothing checks, the drift the generator was
written to end; (C) build the starter `FROM` the CI `ci-base` image, which
bakes the arm cross-compiler and rustup directly rather than through the
index, so the starter would not match what `nros setup` gives a user.

### D2 — What `starter` carries (OPEN, Q3, Q8)

**Recommended:** what the current labs and the book's first chapters need, and
nothing more: the Linux host, `mps2-an385-baremetal` and
`mps2-an385-freertos`, the zenoh backend and its router, C, C++ and a minimal
Rust (host std plus `thumbv7m-none-eabi`), and the crates `nros new`'s
templates pull from crates.io, fetched at build time so a seat behind a NAT
never reaches crates.io. A host C/C++ compiler is required whatever else is
cut: the census sizes every undeclared leaf (RFC-0120 D4). Estimated 4 GB
uncompressed (phase-523 W2's table), under the 2 GB compressed budget (D7) if
the compression ratio holds; not yet measured.

"Lab sources pre-fetched" (phase-523 W2) has no object any more: the labs
scaffold with `nros new`. Whether the image should instead clone a course
repository is Q8.

### D3 — Zephyr as its own target (OPEN, Q4)

**Recommended:** `starter-zephyr` exists but is built on dispatch, not on
every release, until a lab needs it. It adds about 9.5 GB uncompressed, which
is most of a lab network's pull budget (Q9).

### D4 — Audiences are recipes, not images (OPEN, Q3)

**Recommended:** one or two images; each audience gets a documented way of
using them:

- **Newcomer:** `docker run … starter`, then `nros new`. The book's first
  project, offline.
- **Course:** a `devcontainer.json` the course repository commits, naming the
  image by DIGEST, so every seat in a semester opens the same bytes. This is
  phase-523 W2's semester pin, carried by the image instead of by `nros pin`
  alone.
- **Industrial / air-gapped:** `docker save` of a released tag, moved across
  the gap, `docker load`; `nros doctor` reports the running image's digest so
  a support request names what it ran (new: doctor has no container line
  today).

### D5 — A customer derives `FROM` ours, under written guarantees (OPEN)

**Recommended:** a documented, probe-tested recipe
(`FROM ghcr.io/…/nano-ros-starter:<ver>` plus the customer's own boards and
packages), and four guarantees it may rely on:

1. **Immutable version tags.** `<ver>` and `<ver>-zephyr` are never re-pushed.
2. **The baked store matches the release.** The image is built by the release
   from that release's `nros-sdk-index.toml`, so the store it bakes is the
   store `nros setup` of that release resolves. This is what answers
   `runner-container.sh`'s objection: a starter image is pinned to one index,
   and a newer index is a newer tag, not a stale store.
3. **Fixed paths.** `NROS_HOME` and the working directory `/work` do not move
   within a major version.
4. **The recipe is probed.** A probe track builds the documented `FROM` recipe
   against each release.

### D6 — Released with `nros`, tagged three ways (OPEN, Q1, Q5)

**Recommended:** an image job in `release-nros.yml`, after the asset is built.
Tags: immutable `<ver>` and `<ver>-zephyr`; a moving `latest`; and a semester
or LTS retag (e.g. `2027-spring`) that points at one `<ver>` and moves only by
a deliberate retag.

### D7 — An `image` probe track gates `latest` (OPEN, Q9)

**Recommended:** `latest` moves only when a new probe track, `image`, passes:
a TIMED pull of the released tag, then the book's first project built and run
OFFLINE in it. Size budgets, compressed: 2 GB for `starter`, 5 GB for
`starter-zephyr`; over budget fails the track. The pull budget's link speed is
Q9.

### D8 — amd64 first, arm64 next (OPEN, Q6)

**Recommended:** amd64 at first release; arm64 a priority, made possible by
the same runner decision `release-nros.yml:98-100` waits on, since the index
already has the host key.

## Alternatives considered

- **One image per audience.** Four images with overlapping contents, four
  release jobs and four probe tracks; the audiences differ in how they pin and
  start the image, not in what it holds (D4).
- **No image; document `nros setup`.** Today's state. Every seat downloads
  the same toolchains from the release CDN and crates.io, a seat behind a NAT
  or a proxy fails at the first download it cannot reach, and nothing pins a
  semester's seats to the same bytes.
- **Bake into the CI runner image.** The runner deliberately bakes nothing
  (`runner-container.sh:544-551`); a shared `host` target (D1) gets the
  benefit without changing that rule.

## Open questions

The user's, from phase-523 W2's list, widened for the starter audience. Each
names the recommendation above.

- **Q1. Registry.** `ghcr.io/newslabntu/…` public (where `images.yml` already
  publishes the CI images), or a private or university mirror; the image name.
  Recommended: `ghcr.io/newslabntu/nano-ros-starter`, public.
- **Q2. ROS 2 edition.** Humble on 22.04 (the asset's `libpython3.10` floor
  and every probe track today), or Jazzy on 24.04, which needs a 24.04 asset
  build first. Recommended: Humble.
- **Q3. Starter contents.** D2's list; Rust in, or a C/C++-only variant.
  Recommended: D2, Rust in, no variant.
- **Q4. Zephyr.** In a separate `starter-zephyr`, on dispatch (D3), or in
  `starter`, or not at all. Recommended: separate, on dispatch.
- **Q5. Cadence.** Every release (D6), or on dispatch once per semester.
  Recommended: every release, `latest` gated by D7.
- **Q6. arm64.** Wait for the runner decision, or prioritise it now.
  Recommended: amd64 first, arm64 next (D8).
- **Q7. Generator.** Option B (D1), or a hand-written starter Dockerfile (A),
  or `FROM` the CI image (C). Recommended: B.
- **Q8. Lab sources.** Pre-fetch template crates only (D2), or also clone a
  course repository; if so, which and who owns it. Recommended: crates only.
- **Q9. Pull budget.** The link a lab network stands for (100 Mbit/s shared
  by 30 seats, or 1 Gbit/s), which sets D7's timed pull. Recommended: decide
  the link, then let D7's budget follow from it.

This RFC is rewritten from shape to decisions when they are ruled.
