# RFC-0132 -- A board-owned CAN frame driver

**Status:** Draft (2026-11-16, revised 2026-11-17 after the first review).
Review-gated: nothing here is built until the maintainer accepts the shape.
Opened for issue [2633](../issues/2633-board-owned-can-frame-driver.md)
(GitHub #4012); the portable layer under issue
[2573](../issues/2573-can-fd-e2e-profile-and-flexcan-helper.md)'s FlexCAN
helper (GitHub #3761). Work items: phase-560 W9.

## Summary

An application that sends its own CAN or CAN FD frames (an actuator command, an
island-alive heartbeat) has no nano-ros interface to send them through. Each
consumer writes one backend per platform and picks one with `#if`. This RFC
adds a small CAN frame interface to the platform layer: `open`, `send` (with an
FD flag), `fd_active`, an optional `recv`, and `close`. The C header
`<nros/platform_can.h>` is the source of truth (RFC-0054); the Rust side is
committed bindgen output plus a `PlatformCan` implementer trait. The backend
follows from facts the board descriptor already states, and the device is
named in exactly one place per board stack (RFC-0109 D2). The application
keeps its encoder, its frame layout and any end-to-end protection; nano-ros
moves bytes in frames and nothing else.

## Motivation

ASI, the reference consumer, sends control commands on CAN and CAN FD. Its
backend is chosen in `actuation_module/src/asi_common/include/platform/platform_can.h`:

| Backend | Selected by | Device named by |
| --- | --- | --- |
| `zephyr_can.h` | `PLATFORM_ZEPHYR` | `DT_CHOSEN(zephyr_canbus)` |
| `zephyr_can_udp_tunnel.h` | a Kconfig symbol (the FVP has no CAN) | Kconfig peer address and port |
| `freertos_can_socketcan.h` | `PLATFORM_FREERTOS_POSIX` | `getenv("SAFETY_ISLAND_CAN_IFACE")`, `SAFETY_ISLAND_CAN_FORMAT` |
| `freertos_can_mock.h` | `PLATFORM_FREERTOS_CAN_MOCK` | nothing (records frames) |
| `freertos_can_stub.h` | `PLATFORM_FREERTOS` | nothing (fails) |

That chain costs three things:

1. **The census cannot build a host image.** The chain needs a `PLATFORM_*`
   define, which only the board build supplies, so ASI keeps
   `[census] on_missing = "warn"` and its contract is not checked against the
   code.
2. **Run-time facts travel in the environment.** The SocketCAN interface and the
   frame format come from `getenv`, which RFC-0109 and the knob registry both
   refuse as a carrier: nothing records which value an image ran with.
3. **Every consumer re-solves it.** The L4 island needs the same thing on the
   S32K344 (issue 2573: CAN FD to CANHUB), and so will the next one.

The platform ABI has no CAN surface. `packages/drivers/` holds `ipc/`, `net/`
and `serial/`. The zenoh-pico CAN and ISO-TP links (RFC-0080, RFC-0083) carry
the RMW over CAN; they are not an interface an application can send its own
frames through.

## Design

### D1 -- Layers

The split RFC-0109 makes for networks holds here, unchanged:

- **Layer 1 (devices)** belongs to whoever owns the device (RFC-0109 D2):
  Zephyr devicetree (`can0`, `bus-speed`, `bus-speed-data`, `zephyr,canbus`)
  on `stack = "os"`; the host OS (`ip link set can0 type can bitrate ...
  dbitrate ... fd on`) on `stack = "host"`; and on `stack = "board"` the board
  package, from the `[canN]` table in its D4 file. Bring-up stays where
  RFC-0109 D10 put it (`nros-platform-zephyr/src/can_start.c` starts the
  chosen controller; a `"board"`-stack board package starts its own).
- **The frame driver** (this RFC) opens a device that layer 1 brought up and
  sends frames on it. It sets no bitrate, starts no controller, and states no
  layer-1 fact anywhere.
- **The application** owns frame ids, payload layout, whether it sends classic
  or FD frames, and E2E protection (issue 2573's profile is a library over this
  driver, not a part of it).

### D2 -- The ABI: the header is authored, the Rust side is generated

RFC-0054 holds: **the C header is the single source of truth, and Rust consumes
committed bindgen output.** Nothing is generated from Rust.

- **The header** is authored at
  `packages/platform/nros-platform-api/include/nros/platform_can.h`, beside
  `platform_net.h`, and carved out for the same reason: a board with no CAN
  never includes it.
- **The Rust declarations** are generated by `scripts/gen-abi-bindings.sh`:
  `platform_can.h` joins the platform wrapper (`platform.h`, `platform_net.h`
  and `platform_timer.h` today), and its declarations land in the committed
  `packages/platform/nros-platform-cffi/src/generated.rs`. Every name carries
  the `nros_platform_` / `NROS_PLATFORM_` prefix, so the existing allowlist
  (`nros_platform_.*|NROS_PLATFORM_.*`) picks it up with no new pattern.
  `check-abi-bindings` (`gen-abi-bindings.sh --check`) regenerates into a temp
  dir and fails on a diff.
- **The definitions** a Rust backend exports come from a hand-written
  `nros_platform_export_can!` macro in `nros-platform-cffi`, driven by a
  `PlatformCan` trait in `nros-platform-api` (the implementer surface, as
  `PlatformSerial` and `PlatformIvc` are). `check-platform-abi-mirror` gains
  `platform_can.h` in `HEADERS_REQUIRE_MACRO`, so every header symbol must
  appear both in `generated.rs` (allowlist completeness) and in the export
  macro. The C backends (`zephyr`, `socketcan`, `board`) define the symbols
  directly and need no macro.

```c
/* <nros/platform_can.h> -- authored; the Rust side is bindgen output */
#define NROS_PLATFORM_CAN_FLAG_EXT     0x01u  /* 29-bit identifier */
#define NROS_PLATFORM_CAN_FLAG_FD      0x02u  /* CAN FD frame */
#define NROS_PLATFORM_CAN_FLAG_BRS     0x04u  /* FD bit-rate switch */
#define NROS_PLATFORM_CAN_SEND_WAIT_TX 0x80u  /* send: wait for TX completion */

typedef struct {
    uint32_t id;        /* 11- or 29-bit, per NROS_PLATFORM_CAN_FLAG_EXT */
    uint8_t  flags;
    uint8_t  len;       /* payload BYTES: 0..8 classic; 0..8,12,16,20,24,32,48,64 FD */
    uint8_t  data[64];
} nros_platform_can_frame_t;

/* Handle storage: a COMPLETE type whose size this header fixes (D2a). */
#define NROS_PLATFORM_CAN_OPAQUE_U64S 16u
typedef struct {
    uint64_t opaque[NROS_PLATFORM_CAN_OPAQUE_U64S];
} nros_platform_can_t;

/* `device` NULL = the image's device (D4). */
int8_t  nros_platform_can_open(nros_platform_can_t *can, const char *device, uint8_t want_fd);
int8_t  nros_platform_can_send(nros_platform_can_t *can, const nros_platform_can_frame_t *f, uint32_t timeout_us);
uint8_t nros_platform_can_fd_active(const nros_platform_can_t *can);
int8_t  nros_platform_can_recv(nros_platform_can_t *can, nros_platform_can_frame_t *f, uint32_t timeout_us);
void    nros_platform_can_close(nros_platform_can_t *can);
```

- **One send.** `send_fd` in the issue is `send` with
  `NROS_PLATFORM_CAN_FLAG_FD`; a separate entry point would be a second copy of
  the validation. A C++ and a Rust wrapper keep both names for the reader.
- **`len` is bytes, not DLC.** The backend maps bytes to the wire DLC. A length
  that is not a valid FD size is refused, never padded: padding is payload
  layout, which is the application's.
- **Errors are values.** `0` sent, and negative codes (`NROS_PLATFORM_CAN_E*`)
  for: invalid frame (id out of range, bad length, FD flags on a classic open),
  not open, FD not active, queue full or timeout, bus-off, and not supported
  (`recv`, or `NROS_PLATFORM_CAN_SEND_WAIT_TX`, on a backend without it).
  `timeout_us = 0` never blocks.
- **What "sent" means.** `0` means the controller accepted the frame within
  `timeout_us`. With `NROS_PLATFORM_CAN_SEND_WAIT_TX` it means the frame left
  the controller (Zephyr's TX callback). A backend that cannot report
  completion returns "not supported" for that flag; it never downgrades the
  request to acceptance silently.
- **`fd_active`** is true only when the device was opened with `want_fd` and
  the device carries FD (Linux MTU `CANFD_MTU`; Zephyr `CAN_MODE_FD` in the
  controller's capabilities; on a `"board"` stack, a `[canN]` table that states
  a `dbitrate`). Opening with `want_fd` on a classic-only device fails, so an
  image never finds out at its first FD send. Whether to want FD is the
  application's (D1): it is an `open` argument, not a configuration fact.
- **No allocation and no thread.** The handle is caller storage. `recv` polls
  or blocks the caller (open question 2).

### D2a -- How the caller learns the handle's size

A size the build writes per image into a generated header is the sizes-header
class: the per-build `nros_config_generated.h` that two feature shapes wrote
with different sizes (issue 1382), the per-build mirrors that went stale while
their gate compared zero pairs (issue 1792), and the probed `*_OPAQUE_U64S`
macros that had no compile-time check (issue 0472). This handle stays out of
that class:

- **The carrier is the committed header.** `NROS_PLATFORM_CAN_OPAQUE_U64S` is a
  literal in `platform_can.h`, the same on every build, board and road. It is
  ABI: changing it is a header edit, a `gen-abi-bindings.sh` run and a commit
  of both, which `check-abi-bindings` enforces. Rust reads it from
  `generated.rs`, never from a probe, and no build writes it.
- **Every backend proves its state fits.** A C backend states
  `_Static_assert(sizeof(struct <backend>_can) <= sizeof(nros_platform_can_t),
  "NROS_PLATFORM_CAN_OPAQUE_U64S too small for <backend>")` and the same for
  `_Alignof`; the Rust mock states `const _: () = assert!(...)` naming the
  macro. A backend whose state outgrows the storage fails to compile, at the
  backend, naming the constant.
- **The gate is `check-opaque-storage-guards`** (issue 0472), extended: the
  committed header joins its `EMITTERS`, the in-tree backend sources join its
  `GUARD_SITES`, and it learns `_Static_assert` as a guard construct. A new
  in-tree backend without the assert then fails the fast line. An out-of-tree
  `board` backend is outside the gate; the header ships
  `NROS_PLATFORM_CAN_STORAGE_FITS(type)` so its assert is one line.
- **16 u64s (128 bytes)** leaves headroom over the largest state the consumer
  backends carry (a Zephyr device pointer, a `k_sem` for TX completion, a
  receive `k_msgq` pointer and flags, on 64-bit `native_sim`). W9.a records the
  measured `sizeof` of each backend's state beside the constant.

### D3 -- Backends

| Backend | Boards | Device is | Lives in |
| --- | --- | --- | --- |
| `zephyr` | `platform = "zephyr"` (`stack = "os"`), `native_sim` included | a devicetree node: the `nros,can` chosen, else `zephyr,canbus` | `nros-platform-zephyr/src/can.c` |
| `socketcan` | `stack = "host"` boards that are Linux processes: `linux`, `freertos-posix`, `threadx-linux` | an interface name (`can0`, `vcan0`) | `packages/boards/nros-board-linux/c/can_socketcan.c` |
| `board` | `stack = "board"` (FreeRTOS / ThreadX / bare metal with a vendor driver) | a `[canN]` table in the image's D4 file | the board package (strong symbols over weak fail-loud defaults, as `nros_board_register_netif` is today) |
| `mock` | host-process boards only (D5) | ignored | `packages/drivers/can/nros-can-mock` |

- **`zephyr`** is Zephyr's `can_send()` / `can_add_rx_filter_msgq()` over the
  device. On the S32K344 and S32Z270 that device is the FlexCAN or CANXL
  controller, so issue 2573's "raw FlexCAN helper on Zephyr" is this backend
  on those boards, not a separate driver. `native_sim` is a Zephyr board and
  uses this backend over a `zephyr,native-linux-can` node pointed at the host
  interface (RFC-0080's setup), not SocketCAN directly.
- **`socketcan`** is `PF_CAN` / `SOCK_RAW` / `CAN_RAW`, with
  `CAN_RAW_FD_FRAMES` when FD is wanted and the MTU allows it. It is
  Linux-only, so it lives in the board layer, the only layer allowed to be
  Linux-only: `nros-platform-posix` is named for a standard, and
  `check-posix-platform-purity` holds it to one (phase-401 W4; the gate's
  docstring names `nros-board-linux` as the home for Linux-only code).
  `nros-board-linux` is a Rust crate with no C today; W9.c gives it a `c/`
  directory and a `build.rs` (`cc`, `nros-cc-flags`), the shape
  `nros-board-freertos-posix` and `nros-board-threadx-linux` already have.
  Those two Linux-process boards compile the same file by its workspace path,
  as they compile `nros-board-common/c/` today: one source, no copy, and no
  Cargo dependency on `nros-board-linux` (which would bring
  `nros-platform-posix` into a FreeRTOS or ThreadX image). The purity gate
  does not list `PF_CAN`, `CAN_RAW` or `linux/can.h` today; W9.c adds them to
  its `FORBIDDEN` table, so a SocketCAN use in the platform crate is refused
  rather than only discouraged.
- **`board`** is the hook for a vendor stack nano-ros cannot ship (the NXP RTD
  FlexCAN driver on `s32z270-freertos`, GitHub #4015). The board package
  supplies the five symbols; the weak defaults return "not supported", so an
  image whose board supplies none fails at `open`, naming the board.
- **`mock`** records sent frames and replays queued receive frames, with a
  configurable FD capability, so an application's encoder can be tested on the
  host with no interface at all. It replaces each consumer's own mock.

ASI's UDP tunnel (CAN frames over UDP, for an FVP with no CAN controller) is a
consumer protocol, not a CAN backend: its wire format is ASI's. ASI supplies
it through the `board` hook of its own board package (open question 3).

### D4 -- Selection and the device: one table, one carrier per road

The rule is RFC-0103's, as `book-internals/src/pipeline/canonical-build-path.md`
states it: every fact has one authored home, every other copy is generated from
it, and every road reads the resolved answer. The first draft broke it with
three homes (`[board.can]` in the descriptor, an `[image.<id>] can` row, and
RFC-0109's `[can0] bitrate`) carried differently per road. This revision keeps
one.

**The backend is derived, never authored.** It follows from facts the
descriptor already states: `platform = "zephyr"` gives `zephyr`;
`[board.net] stack = "host"` on any other platform gives `socketcan`;
`stack = "board"` gives `board`. There is no `[board.can]` table and no
`driver` key to disagree with the platform. The one authored exception is the
mock (D5).

**The device is named in exactly one home, chosen by the board stack**
(RFC-0109 D2, the predicate that already decides where layer 1 lives):

| `[board.net] stack` | The device is named in | Its layer-1 facts live in | Stating it elsewhere |
| --- | --- | --- | --- |
| `"os"` (Zephyr, `native_sim` too) | the image's devicetree overlay in `os_config`: `chosen { nros,can = &can1; };`, default `zephyr,canbus` | devicetree (`bus-speed`, `bus-speed-data`) | `[image.<id>.can] device` is refused, naming the overlay |
| `"host"` | `[image.<id>.can] device = "vcan0"` in `system.toml` (or `[image_defaults.can]`) | the host OS (`ip link`) | a D4 file is already refused on a host board (RFC-0109 D4) |
| `"board"` | the image's D4 file (`os_config`): its one `[canN]` table, or the one marked `frames = true` when there are several | the same table: `bitrate`, `dbitrate` (RFC-0109 D4/D10) | `[image.<id>.can] device` is refused, naming the D4 file |

So the only new `system.toml` key is `[image.<id>.can]`. It names a device on a
host-stack board and selects the mock (D5); it never holds a bitrate, a
dbitrate or an FD capability. The `[canN]` table is RFC-0109 D4's own (its text
already reserves `[can0] bitrate` for that file); this RFC adds its parser rows
and the `frames` marker, nothing else.

**One carrier per road.** The resolved device travels, with the `[canN]`
layer-1 facts a `"board"`-stack package starts its controller from, in the
carrier RFC-0109 D4 already uses for every interface: `NROS_IMAGE_NET`
(RFC-0103 D10f), as a `can`-kind row. `nros configure` and `nros build` fold it
in `system_net::fold_board_net_files` beside the Ethernet rows, and the codec in
`nros-board-common/src/image_net.rs` stays the carrier's one reader and one
writer, with the new row kind. Per road:

| road | carrier | reader |
| --- | --- | --- |
| cargo | the `NROS_IMAGE_NET` `[env]` row in the generated `nros-cargo.toml` | `nros::main!` bakes it into `DeployOverlay::net`; the board decodes the `can` row at boot and hands the device to the backend for `open(NULL)` |
| cmake | the entry's `IMAGE_NET` argument, compiled as the `NROS_IMAGE_NET` define (`NanoRosEntry.cmake`) | the same decode, from the C board entry |
| west | none from nano-ros: the fact's home is devicetree, which Zephyr carries itself | `DT_CHOSEN(nros_can)`, else `DT_CHOSEN(zephyr_canbus)`, in `can.c` |

No new environment variable, cache variable or Kconfig symbol is added, so no
road gains a carrier (issue 0460/0491's class). W9.e proves delivery the way
`canonical-build-path.md` asks: a non-default device name (`vcan7`) on each
road that carries one, read back from the built image. A non-NULL `device`
argument to `open` still works, for an application that names a second device
in code; the image's table names only the default.

ASI's `SAFETY_ISLAND_CAN_IFACE` becomes `[image.<id>.can] device`; its
`SAFETY_ISLAND_CAN_FORMAT` becomes the application's own `want_fd` argument
(D1: the frame format is the application's).

### D5 -- The mock never reaches hardware

`[image.<id>.can] driver = "mock"` is the one authored backend choice, and it
is legal only on a board that runs as a host process. **"On hardware" is
decided by the board descriptor, from RFC-0118 D4's facts:** a board is a
host-process board when its `[board.run]` states `host = true` and it has no
`[board.flash]` table (today: `linux`, `freertos-posix`, `threadx-linux`, and
`zephyr`, whose `west_board` is `native_sim`). Every other board counts as
hardware, a QEMU or Renode board (`[board.run] emulator = ...`) included,
because its image is the binary that gets flashed.

- **Refused at resolve.** `nros configure` and `nros build` refuse
  `driver = "mock"` on any other board, naming the board, the rule and the two
  descriptor fields read. The census builds a host image, so it may select the
  mock.
- **Refused at compile.** `nros-can-mock` is a host-only crate
  (`[package.metadata.nros] host-only = true`, as `nros-board-linux` is), and
  its `lib.rs` carries `#[cfg(target_os = "none")] compile_error!(...)`, so a
  bare-metal or RTOS cross build that reached it by any path stops there.
- **Absent at link.** The mock is the one backend not derived from the board
  (D4). It is linked only when the resolved `can` row says `mock`, so a
  hardware image has no mock symbols to resolve against.

### D6 -- What the build checks

- An image that names a CAN device on a board whose `links` lacks `can` is
  refused by `nros configure`, naming the board (RFC-0109 D3's link
  vocabulary). `freertos-posix` and `threadx-linux` gain `can` in their
  `links` (W9.c); `linux` and `zephyr` already state it.
- `[image.<id>.can] device` on an `"os"` or `"board"` stack, or a `[canN]`
  table on a host stack, is refused, naming the right home (RFC-0109 D9.6).
- `driver = "mock"` on a board that is not a host-process board is refused
  (D5).
- On a `"board"` stack, several `[canN]` tables with no `frames = true`, or
  more than one marked, are refused.
- The census builds a host image with the `mock` backend, so a consumer whose
  only `PLATFORM_*` dependency was its CAN chain can set `[census] on_missing`
  back to `error`.

## Alternatives considered

- **Keep CAN in the application (status quo).** Every consumer writes the same
  five backends, and the census cannot build them. Rejected for the reasons in
  the Motivation.
- **Generate the C ABI from a Rust trait with cbindgen** (the first draft).
  Reverses RFC-0054, which made the headers the source of truth after the
  hand-kept Rust/C mirror drifted three times. Rejected.
- **`can_socketcan.c` in `nros-platform-posix` behind `#ifdef __linux__`.** The
  purity gate accepts a guarded line, but the crate's name is the claim the
  gate protects, and Linux-only code belongs in the board layer. Rejected.
- **A descriptor `[board.can]` table** (the first draft). A second home for a
  fact the board stack already locates, and a `driver` key that can disagree
  with the platform. Rejected for D4's derivation.
- **A per-build size for the handle** (an `nros_config_generated.h` macro
  probed from the backend). The sizes-header class (D2a). Rejected.
- **Ride zenoh-pico's CAN link.** RFC-0080 keeps that link self-contained in the
  vendored tree, and it carries zenoh's own framing; an application frame with
  a fixed id and layout (a CANHUB command) cannot go through it (open
  question 4).
- **A header-only C++ helper** (what ASI has, moved into nano-ros). It keeps the
  `#if` chain and still needs a platform define, so the census problem stays.
- **Zephyr only, for issue 2573.** It solves the K344 and leaves the SocketCAN,
  mock and FreeRTOS halves to each consumer again.

## Open questions (resolved in the 2026-11-17 revision)

1. **Send completion.** *Resolved:* acceptance by default;
   `NROS_PLATFORM_CAN_SEND_WAIT_TX` waits for completion where the backend
   reports it (Zephyr's TX callback in the first build). SocketCAN and the
   `board` hook return "not supported" for the flag until a consumer needs it
   (`CAN_RAW_RECV_OWN_MSGS` is the SocketCAN route then). Never a silent
   downgrade.
2. **Receive into the executor.** *Resolved, deferred by design:* polled or
   blocking `recv` only. Both first consumers only send. A readiness callback
   into the executor (RFC-0084) is additive to the header, and the first
   consumer that receives designs it; issue 2633 records that trigger.
3. **Consumer backends.** *Resolved:* only through the image's own board
   package's `board` hook. No named-backend registry, so the backend stays
   derived (D4). ASI owns its UDP tunnel, in its FVP board package.
4. **Sharing with the zenoh-pico CAN link.** *Resolved here; the rebase is
   owned by the RFC-0080 / RFC-0083 link work:* no rebase in this RFC. On
   `"os"` and `"host"` stacks the OS shares a device between the link and the
   frame driver (Zephyr RX filters, independent SocketCAN sockets), so both may
   open it. On a `"board"` stack, where a vendor driver may not share, an image
   whose RMW wiring and frame driver name the same `[canN]` is refused at
   configure. Rebasing the link onto this driver is a follow-up issue W9.f
   files against the link.
5. **Multiple devices.** *Resolved:* one default device per image. A second
   device is opened by name in code (`open("can1", ...)`). A keyed table
   (`[image.<id>.can.<name>]`, several `frames` markers) waits for a consumer
   that needs two defaults; the shape is additive.
