# nano-ros Examples

Copy-out templates for users porting nano-ros to a new platform and language.

**Non-example binaries live elsewhere** — see [Where else to look](#where-else-to-look).

## Tree shape

```
examples/
├── <platform>/<language>/<example>/           # canonical
├── workspaces/<language-or-mix>/              # Node + Bringup + Entry workspaces
└── templates/<name>/                          # multi-platform recipes (Pattern A workspace, etc.)
```

- **Platform** (9): `linux`, `px4`, `mps2-an385-baremetal`, `mps2-an385-freertos`, `qemu-armv7a-nuttx`, `rv-virt-nuttx`, `rv-virt-threadx`, `threadx-linux`, `zephyr`
- **Language**: `c`, `cpp`, `rust`
- **Example** (cases): `talker`, `listener`, `service-{server,client}`, `action-{server,client}`, `custom-msg`, plus variant suffixes: `-rtic` (linux only; on mps2-an385 RTIC is a workspace image), `-aemv8r`, etc.

**One example serves every RMW backend.** The path is
`<platform>/<language>/<example>`, with no `<rmw>/` level: the backend is
part of the deployment, stated in the example's `system.toml` (below).

The PX4 tree is the exception in shape, because PX4's own build consumes it:
see [`px4/README.md`](px4/README.md).

Each example is a standalone Cargo or CMake package: no walk-up in the
manifests, no workspace coupling. Copy it out and build it:

- **Rust** — manifests declare nano-ros crates registry-style (`nros = { version = "*" }`) and carry Rust-toolchain facts only. Which board the leaf deploys to is stated once, in `system.toml` beside the manifest (`[image.<id>] board`); `nros configure` turns that choice into the generated build settings under `build/<image>/`, and `nros build` reads them. Copy the directory anywhere, put your checkout's `nros` on PATH, and build:

  ```bash
  cp -r examples/linux/rust/talker ~/my-talker && cd ~/my-talker   # a one-node workspace
  source /path/to/nano-ros/activate.sh   # puts that checkout's nros on PATH
  nros build linux   # its bringup's system.toml names the image
  ```

  Driving cargo yourself is supported — hand it the file `nros configure` wrote. Run it from the directory *above* the package: the leaf's own `.cargo/` still exists and cargo would read it a second time.

  ```bash
  cd ~
  cargo build --manifest-path my-talker/Cargo.toml \
              --config my-talker/build/linux/nros-cargo.toml
  ```

  A single-package **Rust** leaf is its own entry, and on a supported board it names no board crate: it depends on `<pkg>_nros_selection = { path = "build/nros/selection" }`, which `nros configure` / `nros build` generate with the image's board crate, RMW backend and runtime crates, so switching it to another board is the `[image.*] board` line, as it is for a C/C++ leaf and a workspace.

- **Workspaces** — `examples/workspaces/<ws>/` is copy-out as a whole, by the same rule: its packages name nano-ros crates by version and `nros configure` writes the patch for every member. A `path` dependency stays inside the copy (a sibling package, a `generated/` message crate); one that leaves `examples/` is refused by `just check example-path-deps`.

  ```bash
  cp -r examples/workspaces/launch ~/my_robot && cd ~/my_robot
  source /path/to/nano-ros/activate.sh
  nros configure && nros build
  ```

- **C / C++** — every CMakeLists finds nano-ros with `find_package(nano_ros)`, and a copied-out leaf names the checkout with `-Dnano_ros_ROOT=<path>`, the hint that call reads (`nros build` passes it for you). That hint says where the checkout is and nothing else — the board, the RMW, the domain and the network identity come from the leaf's `system.toml`, not from `-D` flags and not from the retired `package.xml` `<nano_ros deploy= board= rmw=/>` tuple. A single-package C/C++ leaf needs no `nros configure`: its message bindings are a CMake-time output. Copy the directory anywhere, then:

  ```bash
  cp -r examples/linux/c/talker ~/my-c-talker && cd ~/my-c-talker
  cmake -S . -B build -Dnano_ros_ROOT=/path/to/nano-ros   # or: nros build
  cmake --build build
  ```

  (Or `nros build` in the leaf: it runs the same pair into `build/<image>/cmake`, with the board's toolchain file.)

- Every canonical leaf ships its own `README.md` with the copy-out build/run steps and the `system.toml` that carries its deployment — the instructions travel with the directory. They are generated by [`scripts/docs/gen-example-readmes.py`](../scripts/docs/gen-example-readmes.py) (`--force` re-renders the generated pages after a template change; hand-written pages are never overwritten) and gated by `example_shape::every_canonical_leaf_has_readme`.

- Prefer vendoring the checkout into your own workspace instead? See [`templates/multi-package-workspace/`](templates/multi-package-workspace/), which documents the path-dep Pattern A layout.

Embedded targets locate their SDK trees through `nros` (the board descriptor states board facts such as the FreeRTOS port) — `source activate.sh` in the nano-ros checkout puts it on PATH. The RMW is part of the deployment, so it is stated with the rest of it: `[system] rmw = "<backend>"` in the leaf's (or bringup's) `system.toml`, in one place for every language. Supported backend names are `zenoh`, `xrce`, `cyclonedds`, and `uorb`.. Zephyr keeps its own front-end on top — the `prj-<backend>.conf` Kconfig overlay a west build selects.

### ROS editions

Every example builds for each ROS edition (`humble`, `iron`, `jazzy`); the
edition is chosen per build, not per example. The zenoh interop with ROS 2
needs `rmw_zenoh_cpp` in that edition's install: Humble ships it as
`ros-humble-rmw-zenoh-cpp`, as does Jazzy. Cyclone DDS and XRCE-DDS interop
work with every edition.

### Intentionally empty cells

These cells are blank on purpose.

| Cell | Why empty | Lift requires |
|---|---|---|
| `px4/{c,rust}/*` (px4 has no example-tree uORB cell) | PX4 integration is uORB-only (the platform's native pub/sub), and `nros-rmw-uorb` is a single C++ port; the Rust crate was deleted. `packages/testing/nros-px4-register-check/` is the canonical surface. | Won't lift: C is not on the PX4 module API, and the Rust uORB backend is gone. No C or Rust PX4 examples are planned. |
| `cyclonedds` on bare-metal (`mps2-an385-baremetal`) | Cyclone DDS requires a hosted runtime: BSD sockets, threads, heap, libc. A bare-metal Cortex-M target has none. | Won't lift on bare-metal. Embedded targets use the zenoh-pico or XRCE-DDS backends. |
| `cyclonedds` on NuttX QEMU (`qemu-armv7a-nuttx`, all languages) | A Cyclone DDS socket-shim port to NuttX is upstream-scale work, not attempted in nano-ros. (FreeRTOS has Cyclone fixtures over lwIP.) | An upstream Cyclone DDS NuttX port (socket shim, config, heap budget), then an example cell. |
| pure-cargo `cyclonedds` Rust binaries on `linux` / `threadx-linux` | `nros-rmw-cyclonedds-sys` exposes only the C register shim, so a plain Cargo build cannot build and link the C++ Cyclone library and `libddsc`. Native Rust Cyclone uses the CMake/Corrosion path instead. | Use the CMake/Corrosion path for Cyclone-backed Rust examples. |
| `cyclonedds` service/action on `rv-virt-threadx` (`c`/`cpp`): talker and listener only | Cyclone on ThreadX RISC-V64 is experimental; its participant init is still being diagnosed. Only talker/listener are wired, run by a two-QEMU pub/sub test. Service/action need two-way RTPS discovery over that link, unproven on this port; zenoh covers all six roles here. | The participant-init fix, then a two-QEMU Cyclone request/response test. |
| `zephyr/rust/service-client-async` | Dropped, with its native tokio sibling: async-runtime integration was retired because a foreign scheduler would decide when callbacks run. | None: not coming back while the real-time promise is the support rule. |

## Sibling categories

### Cross-RMW bridges live in `workspaces/`, not a category of their own

There is no `bridges/` category. It held two hand-written time-triggered
gateways (`tt-zenoh-to-xrce`, `tt-zenoh-to-cyclonedds`) that no fixture row,
lane or `system.toml` ever built, and they were deleted. A
bridge is a `[[bridge]]` row in a workspace's `system.toml`:
[`workspaces/bridge-cyclonedds/`](workspaces/bridge-cyclonedds/) and
[`workspaces/bridge-xrce/`](workspaces/bridge-xrce/) below, both built and
e2e-tested. See
[`book/src/guide/rmw/bridge-between-backends.md`](../book/src/guide/rmw/bridge-between-backends.md)
for the model and the build knobs.

### `workspaces/` — product-shaped multi-package workspaces

Workspaces that follow the book's Node package + Bringup package workflow. A
workspace is a directory of packages — no root `Cargo.toml`, no root
`CMakeLists.txt`, and no entry package to write: the entry is generated per
`[image.*]`. Build one with

```bash
cd <ws>
nros configure
nros build              # every [image.*]; or: nros build <image-id>
```

Everything generated lands under `build/`, `dist/` and `log/`. Zephyr stays the
carve-out: `west build` is still its build verb, with `nros configure` before it.


**A feature is a node package and a configuration is a fixture axis — never
a new directory.** QoS, params, lifecycle, custom messages and remap are
demonstrated together in `features/`; message integrity in `safety/`.
Naming rules:
[`docs/development/example-workspace-layout.md`](../docs/development/example-workspace-layout.md).

Every workspace has its own README; one line each. Recount with
`ls -d examples/workspaces/*/` rather than trusting this list:

| Workspace | What it shows |
| --- | --- |
| `rust/` | base starter: Rust Node pkgs + the Node / Bringup / Entry split in pure Rust |
| `c/` | base starter: C Node pkgs |
| `cpp/` | base starter: C++ Node pkgs |
| `mixed/` | the language SEAM: one entry, components from C, C++ and Rust |
| `features/` | the capability demos in one workspace — params, lifecycle, QoS, custom messages, remap — native only |
| `safety/` | E2E message integrity in one workspace (auto CRC-32 + seq, validated subscription reports faults) |
| `bridge-cyclonedds/` | declarative `[[bridge]]`: `/chatter` zenoh → cyclonedds in one process, no user bridge code |
| `bridge-xrce/` | the same declarative bridge, XRCE variant (zenoh → XRCE Agent → DDS) |
| `launch/` | advanced launch composition — topology lives in the launch XML (launch v1) |
| `managed/` | the lifecycle shape `features/` cannot hold: a C++ node that manages ITSELF |
| `realtime-c/` | two nodes on two sched tasks (`/ctrl` 10 ms high, `/telem` 100 ms low) from config |
| `realtime-cpp/` | the C++ base of the same two-sched-task scheduling differentiator |
| `realtime-cpp-subnode-portable/` | the identical `SubNode` under tiers renamed `fast`/`bulk` — tier names are deployment-owned |
| `realtime-rust/` | the Rust projection of the scheduling-sched-tasks differentiator |
| `derived-sched-tasks-cpp/` | four C++ components and **no authored sched tasks** — a sizing fixture shaped like a real safety controller |
| `sizing/` | a node the SystemModel cannot count (six timers, no subscription) — the executor-sizing showcase |
| `island-shaped/` | the layouts a real safety-controller project hit, built in CI: sibling-package param files, C + Rust in one image, raised pools, census + board build |

### `templates/` — multi-platform copy-out recipes

Patterns that span platforms (multi-package workspace layouts, mixed C / C++ / Rust packages sharing one nano-ros install, etc.).

- `templates/multi-package-workspace/` — Pattern A workspace (C talker, C++ listener, Rust publisher under one nano-ros install). It declares **no** workspace root by either tracked spelling and has no bringup: it is the path-dep pattern, not a colcon workspace, so `nros build` does not drive it.
- `templates/local-msg-package/` and `templates/workspace-shadowing/` are workspaces with no bringup: a `.colcon_workspace` and packages. `nros build` builds every package in dependency order, colcon's default. `workspace-shadowing` carries no `system.toml` at all; `local-msg-package` carries one beside a *package*.

## Where else to look

Test / bench / smoke binaries are NOT under `examples/`. They live with the integration-test crate so the example tree stays a clean copy-out surface.

- **`packages/testing/nros-bench/`** — perf, fairness, stress, large-msg
  - `executor-fairness`, `stress-{zenoh,xrce}`, `large-msg-{xrce,baremetal}`, `wcet-cycles-qemu`
- **`packages/testing/nros-smoke/`** — driver / board bringup (no nros API)
  - `stm32f4-smoltcp-echo`
- **`packages/testing/nros-tests/bins/`** — fixture binaries that integration tests build & invoke
  - `cdr-roundtrip-qemu`, `lan9118-qemu`
- **`packages/testing/nros-px4-register-check/`** — PX4 module whose *build* is the assertion
  - links `nros-rmw-uorb` inside a real `px4_add_module()` context against real
    PX4 headers; run via `just px4 build-sitl-cpp`.

Each is a standalone Cargo package with an empty `[workspace]` table (they nest under the `nros-tests` workspace member).

## Consumption profile per platform

Each `examples/<plat>/` tree maps to one of the seven consumption
profiles from [`book/src/extending/add-a-board.md`](../book/src/extending/add-a-board.md).
The mapping tells you which guide to read when porting one of these
examples to your own board.

| `examples/<plat>/` | Profile | Guide |
|---|---|---|
| `linux/` | Host (Linux) | `nros configure` + `nros build` — no integration shell needed. |
| `mps2-an385-baremetal/` | Cargo-first bare-metal | [Generic board crate](../book/src/extending/add-a-board.md#before-you-start) (`nros-board-baremetal-cortex-m`) |
| `mps2-an385-freertos/` | Cargo-first FreeRTOS | [Generic board crate](../book/src/extending/add-a-board.md#before-you-start) (`nros-board-freertos`); reference overlay `nros-board-mps2-an385-freertos`. For STM32 / NXP / Espressif FreeRTOS, write a [vendor overlay](../book/src/extending/add-a-board.md). |
| `qemu-armv7a-nuttx/` | NuttX native shell | [NuttX integration shell](../book/src/guide/platforms/nuttx.md) — `apps/external/nano-ros/`. |
| `rv-virt-threadx/` | Cargo-first ThreadX | [Generic board crate](../book/src/extending/add-a-board.md#before-you-start) (`nros-board-threadx`); reference overlay `nros-board-threadx-qemu-riscv64`. For Renesas Synergy / STM32 X-CUBE-AZRTOS / NXP MCUXpresso ThreadX, write a [vendor overlay](../book/src/extending/add-a-board.md). |
| `threadx-linux/` | Linux sim (CI) | Same as `rv-virt-threadx` but with NSOS host-kernel sockets shim. |
| `zephyr/` | Zephyr native shell | [Zephyr integration shell](../book/src/guide/platforms/zephyr.md) — `projects:` entry in your `west.yml`. |
| `px4/` | PX4 native shell | [PX4 integration shell](../book/src/guide/platforms/px4.md) — `EXTERNAL_MODULES_LOCATION`. |

When in doubt, read [Board Integration](../book/src/extending/add-a-board.md)
first — it explains why each profile exists and which one fits your
project's build system.

## Quick start

Each block assumes a zenoh router running on `tcp/127.0.0.1:7447` — `ros2 run rmw_zenoh_cpp rmw_zenohd` (contributor shortcut inside a checkout: `just linux zenohd`). C/C++ examples find nano-ros with `find_package(nano_ros)`, given `-Dnano_ros_ROOT` as the copy-out contract above describes; no install step required.

### Native Rust + zenoh

```bash
# terminal 2
cd examples/linux/rust/talker && nros run linux   # a one-node workspace

# terminal 3
cd examples/linux/rust/listener && nros run linux   # a one-node workspace
```

### QEMU bare-metal Cortex-M3 (MPS2-AN385)

```bash
just setup qemu
just qemu build
just qemu talker      # spawns QEMU + nros-rs-talker
```

### Zephyr (native_sim) C + Cyclone DDS

```bash
just setup zephyr
source ~/nano-ros-workspace/env.sh
cd nano-ros/examples/zephyr/c/talker
nros build nros_zephyr_talker_c_bringup:zephyr_cyclonedds
# the build prints the west build directory; run its zephyr/zephyr.exe
```

## ROS 2 interoperability

nano-ros pubs/subs are rmw_zenoh-compatible. Quickest round-trip:

```bash
# terminal 1
ros2 run rmw_zenoh_cpp rmw_zenohd

# terminal 2
cd examples/linux/rust/talker && nros run linux   # a one-node workspace

# terminal 3
source /opt/ros/humble/setup.bash
export RMW_IMPLEMENTATION=rmw_zenoh_cpp
ros2 topic echo /chatter std_msgs/msg/String --qos-reliability best_effort
```

For DDS-side interop (cyclonedds), see `docs/reference/rmw_zenoh_interop.md`.
