A scheduling tier is a **sched task** in nano-ros's own names (phase 536 W2; the table is RFC-0052 "Names"), following rlm and play_launch, which call it a task. The C ABI: `nros_native_tier_spec_t`, `nros_tier_task_memory_t` and `nros_tier_backing_t` are `nros_native_sched_task_spec_t`, `nros_sched_task_memory_t` and `nros_sched_task_backing_t`; `nros_board_<rtos>_run_tiers{,_ns,_in,_backed_in}` are `..._run_sched_tasks{...}` and `..._run_tiers_tasks_in` is `..._run_sched_tasks_memory_in`; `<rclc/detail/tier_task_memory_<rtos>.h>` and its `NROS_TIER_TASK_MEMORY*` macros are `<rclc/detail/sched_task_memory_<rtos>.h>` and `NROS_SCHED_TASK_MEMORY*`. The old C names, the C++ `NativeTierSpec` / `run_tiers` and PX4's `TierWorkItem` / `<nros_px4/tier_work_item.hpp>` still build for one release, each use warning with the new name (`NROS_NO_DEPRECATED_TIER_NAMES` drops them early); the struct field `tier_class` is `sched_task_class` with no alias. Kconfig: `CONFIG_NROS_ZEPHYR_MAX_TIERS`, `CONFIG_NROS_ZEPHYR_TIER_STACK_SIZE` and `CONFIG_NROS_ZEPHYR_TIER_STACKS_IN_DTCM` are `CONFIG_NROS_ZEPHYR_MAX_SCHED_TASKS`, `CONFIG_NROS_ZEPHYR_SCHED_TASK_STACK_SIZE` and `CONFIG_NROS_ZEPHYR_SCHED_TASK_STACKS_IN_DTCM`; the old symbols still feed the new ones for one release, and the configure warns when a `.conf` file sets one. Rust items are renamed with no alias (`TierSpec` is `SchedTaskSpec`, `TierExecutorBacking` is `SchedTaskExecutorBacking`, `nros_platform::board::tier` is `board::sched_task`, ...). The example workspace `derived-tiers-cpp` is `derived-sched-tasks-cpp`, and the `check tier-priority-plan{,-image}` / `tier-spin-gap` gates are `sched-task-...`.
