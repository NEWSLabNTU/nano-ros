`nros::InitError::LaunchParseFailed` is removed. Nothing ever returned it: it waited on an in-process launch-file parse that will not be built, because launch content reaches an image at build time (`nros sync` resolves the launch tree into the SystemModel and the generated entry installs it). A `match` that names the variant drops that arm. The `init_with_launch*` docs (Rust and C++) no longer describe a `NROS_RUNTIME_OVERLAY` sidecar or an `nros launch` verb — neither exists (issue 1917).

`nros::ContextSource::Launch` is removed as well, and so are the entry points it tagged: `nros::init_with_launch_auto()`, `nros::init_with_launch(path)` and `nros::InitError::LaunchFileNotFound` (which only the latter returned), and the C++ `rclcpp::init_with_launch_auto(argc, argv)` / `rclcpp::init_with_launch(path, argc, argv)`. None read a launch file — each read the environment (and, in C++, `--ros-args`) exactly as the call that replaces it does, so `Launch` claimed something that never happened, while `nros::main!(launch = …)`, the entry that does install launch content, reported `Env`. Replace `nros::init_with_launch_auto()` and `nros::init_with_launch(path)` with `nros::init()`, and the C++ pair with `rclcpp::init_in(argc, argv)`; check the path yourself if you relied on the existence check. A project scaffolded by `nros new` before this release calls `nros::init_with_launch_auto()` and no longer compiles until that one line changes (issues 1917, 1931).
