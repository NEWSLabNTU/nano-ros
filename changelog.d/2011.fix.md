C++ action futures are keyed by their goal. `rclcpp_action::Client<A>::
get_result_future` used to read a process-global one-slot result buffer shared
by every C++ action client, so two goals (or two clients) could read each
other's result; `send_goal_future` raced the executor's dispatch and missed an
acceptance taken during `spin_once`. Each future now waits on its client's own
list under its goal id: it receives only that goal's acceptance or result,
whichever path took the reply, and a result nobody waits on is dropped. The
blocking `send_goal` / `get_result` wait for their own goal and forward every
other reply instead of swallowing it, the feedback stream keeps the latest
feedback per client rather than per process, and a full table refuses the send
(empty future). The L1 polled action clients gain
`rclc_polling_action_client_try_recv_{goal_response,result,cancel_response}_raw_for`
(C) and `goal_id_out` overloads on `PollingActionClient` (C++), which report the
goal each reply is about.
