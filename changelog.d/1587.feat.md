A managed node now announces its transitions on `~/transition_event`, so a supervising node can watch a lifecycle node passively instead of polling `~/get_state`. `register_lifecycle_services` creates the `lifecycle_msgs/msg/TransitionEvent` publisher REP-2002 requires beside the five services, `LifecyclePollingNodeCtx::trigger_transition` records every transition it performs — the one function `ros2 lifecycle set`, the C and C++ `change_state` shims, `autostart` and the safe `LifecycleCallbacks` road all funnel through — and the executor drains the record onto the wire during `spin_once`. Failed transitions are announced too, because the failure is what a supervisor needs to see; rejected ones are not, because none ran. The QoS is upstream's, MEASURED rather than assumed: `ros2 topic info -v` on a live humble `lifecycle_talker` reports RELIABLE / VOLATILE, i.e. `rmw_qos_profile_default`, so the publisher costs one publisher slot and one liveliness token per lifecycle-enabled image and **no queryable** — phase-467's study had priced this row as its most expensive on the premise that the topic is TRANSIENT_LOCAL, which would have put a sixth slot into a `ZPICO_MAX_QUERYABLES` that defaults to 8 against the eleven `[param_services]` and `[lifecycle]` already claim. `InfraServices::publishers` carries the new slot into `EntityInventory::derive`, and `check-infra-queryable-counts` holds the count to its creation site.
