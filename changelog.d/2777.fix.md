A cargo project whose board dependencies come from its generated selection package now gets a parameter store when it serves the parameter services, including the stock ones every image gets by default. Before this, such an image built no store, asked the heap for the full 32-slot store (about 283 KB) at startup, and exited when the heap refused it. The ThreadX Linux listener did exactly that.

A Rust image that serves the parameter services but whose build sets aside no parameter store now fails to build, and the error names the `max_parameters` knob. It no longer boots and then fails one large heap allocation. The runtime's own store refusals name the knob in the same words.

That build error now also says how to build the image: with `nros build`, or with cargo after `nros configure`, as `cargo build --config build/<image>/nros-cargo.toml` for the image it names. A package inside a workspace that declares its own image now gets that settings file from `nros sync` and is built by `nros build` the same way a lone package is, so the parameter store is sized for it too.
